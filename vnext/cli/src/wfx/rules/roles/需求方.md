# 需求方

你是這張卡的最終需求方。框架成敗只看四件事（flow.md §1），其中一件是**你用框架是否比自己直接管 AI 更省力**——覺得不省力就說出來，那是需求問題，不是你該忍的成本。

## 1 · 定義成果

需求階段你與 PM 一起把四組事情講清楚：

- 要解決的問題與**單一主要成果**；
- 限制、非目標與已知假設；
- 風險、影響、緊急性與期限；
- **能直接檢查的驗收條件**。

需求階段必須執行 **Grilling**：逐項提問，檢查目標、成果、限制、非目標、假設、風險與驗收之間有沒有矛盾。Grilling 只問「要什麼」與「為什麼」，⛔ 不做事實研究、技術比較或方案設計；需要查證現況時進研究子狀態（research.md）。

需求核定即**鎖定成果方向**（flow.md §3）。之後任何方向改動都會停下當前階段回到你這裡。

## 2 · 階段確認

每個正式階段完成時由你確認，一次只看**一個畫面**：成果、疑慮、下一步。

- 研究子狀態、正常實作修正、測試重跑、非阻擋觀察⛔ 都不會多找你一次。
- 一個畫面裝不下就當場說，由你決定怎麼呈現；⛔ 不拆新卡、⛔ 不加確認次數。
- **合併需要你的授權**，那是結案階段確認的一部分（flow.md §8）。
- 緊急性只影響排程，⛔ 不降低需求確認、執行自檢、獨立審核或結案證據的要求。

## 3 · 只有你能裁定的事

方向、成本、風險接受、公開契約、任務是否停止，以及框架級／使用者級注意事項的核定。

PM ⛔ 不做技術裁決。技術爭議先由獨立內容角色釐清，仍無法收斂才上到你這裡。內容角色可以建議退回或停止，但決定權在你。

裁定可在對話或 GitHub 給出。**對話裁定由 PM 忠實登記成留言（裁定者／內容／時間）後才算數**，未登記的⛔ 不得作為派工輸入（github.md §4）。

## 4 · 階段確認不是審核

你可以兼任執行者，但⛔ 不得擔任該成果的正式審核者——**階段確認≠正式審核**（independence.md §1）。你按下確認，不代表成果已被獨立核對過。

## 5 · 你維護的模型資料

使用者層 `~/.wf/` 的兩類模型資料由你維護：**穩定**的使用說明（家族劃分、各自適合什麼、呼叫慣例）與**短期**的可用性備註（每則只記來源與最後確認時間）。

⛔ 不放憑證。框架層與專案層⛔ 不得寫入具體模型名稱、額度數字或帳號狀態（boundaries.md §2）。新鮮度由 PM 在派工當下自行判斷，⛔ 不建自動過期或額度查詢。
