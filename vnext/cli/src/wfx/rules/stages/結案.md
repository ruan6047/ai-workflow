# 結案階段

讀者＝在這個階段實際動手的人：**PM**。

## 1 · 固定序（順序不可調換）

1. **PM 整理結案卡。**
2. 在該卡的階段確認中取得**需求方的合併授權**。
3. **PM 合併。**
4. **驗證合併結果**：合併目標分支（一般為 `main`）、CI 與正式成果。
5. 驗證結論寫進**同一則**結案留言。
6. **關閉任務並完成必要清理。**

**未取得需求方合併授權⛔ 不得合併**；**未完成驗證⛔ 不得關卡**。這一序⛔ 不新增例行確認點：合併授權就在本階段那一次確認裡取得，驗證結論回到同一則留言，⛔ 不為驗證另發一次確認、⛔ 不另開一則留言。

## 2 · 結案卡要放什麼

一個畫面內：**主要成果與其直接證據、審核結論、合併目標與範圍、未驗證項、關卡後的清理項**。

**未驗證項要如實列出**——沒跑到的、沒自然發生而只做有界演練的、環境不足而「無法判定」的，都標明，⛔ 不得以「應該沒問題」帶過。

## 3 · 合併後驗證失敗

**失敗與本次成果有關 ⇒ 原卡不得結案。**

PM 標記**阻塞**，修正或回滾一律**退回執行階段**處理，再重新經過審核與結案。被退回的階段重新完成後必須**重新確認**——這不是增生（flow.md §4）。

**只有確認失敗與本次成果無關**，才能另開任務處理；即使如此，**原卡仍須具備自己的完成證據**才能結案。

判定「有關／無關」是技術判斷：**PM ⛔ 不做技術裁決**，交由適當的獨立內容角色釐清，仍無法收斂才交需求方裁定（boundaries.md §6）。

## 4 · 本階段⛔ 不修改成果內容

程式碼、測試、文件、設定、資料與框架規則在本階段**一律不動**。要改就是退回執行階段。

開下一張卡、關閉本卡是**平台協調操作**，不是成果內容；以 `gh issue create --body-file`、`gh project item-add`、`gh issue close` 執行（github.md §5）。

## 5 · 收尾檢查

- 七個核心概念的**最終值**已寫入，且與實際情況一致。
- 結案留言存在且含驗證結論；`## 裁定紀錄` 的索引指得到合併授權那則留言。
- 資源租用已釋放；狀態不明時標示「狀態未知」，下一位使用者⛔ 不得直接寫入（github.md §6）。
- 卡片級注意事項候選已登記；提升為專案層以上者，需求方確認後由執行者改正式文件（boundaries.md §7）。
