# 結案階段

讀者＝在這個階段實際動手的人：**PM**。

## 1 · 固定序（順序不可調換）

1. **PM 整理結案卡。**
2. **核對審核階段確認已裁定的授權範圍**（stages/審核.md §7），並客觀比對受審版本的基準 SHA 與當前合併目標分支（一般為 `main`）；不同就照 flow.md §6 退回審核，⛔ 不合併。
3. **PM 合併。**（無合併動作的成果略過，如研究答案路徑，flow.md §4）
4. **驗證合併結果**：合併目標分支（一般為 `main`）、CI 與正式成果；無合併時驗證成果識別仍可取得。
5. 驗證結論寫進**同一則**結案留言。
6. **關閉任務並完成必要清理。**

**授權未涵蓋的動作⛔ 不得執行**——授權只涵蓋審核確認當下已知的動作，未涵蓋的新動作須在**發生前**取得需求方授權；**未完成驗證⛔ 不得關卡**。本階段**只執行已授權動作並回報實際結果，⛔ 不另設批准**，也⛔ 不新增例行確認點：驗證結論回到同一則結案留言，⛔ 不為驗證另發一次確認、⛔ 不另開一則留言。

## 2 · 結案卡要放什麼

一個畫面內：**主要成果與其直接證據、審核結論、合併目標與範圍、未驗證項、關卡後的清理項**。

**未驗證項要如實列出**——沒跑到的、沒自然發生而只做有界演練的、環境不足而「無法判定」的，都標明，⛔ 不得以「應該沒問題」帶過。

## 3 · 合併後驗證失敗

**失敗與本次成果有關 ⇒ 原卡不得結案。**

PM 標記**阻塞**，修正或回滾一律**退回執行階段**處理，再重新經過審核與結案。被退回的階段重新完成後，照該路徑需確認的正式階段**重新確認**（執行階段不確認，重新完成且符合原核定審核安排後直接再送審）——這不是增生（flow.md §4）。

**只有確認失敗與本次成果無關**，才能另開任務處理；即使如此，**原卡仍須具備自己的完成證據**才能結案。

判定「有關／無關」是技術判斷：**PM ⛔ 不做技術裁決**，交由適當的獨立內容角色釐清，仍無法收斂才交需求方裁定（boundaries.md §6）。

## 4 · 本階段⛔ 不修改成果內容

程式碼、測試、文件、設定、資料與框架規則在本階段**不修改**；需要改受審成果就退回執行。已確認經驗僅依 boundaries.md §7 的使用者層受控落地／專案或框架已定案改動卡承接處理，⛔ 不由 PM 修改內容，⛔ 不改已批准產品 PR 的受審 SHA。

開下一張卡、關閉本卡是**平台協調操作**，不是成果內容；以 `gh issue create --body-file`、`gh project item-add`、`gh issue close` 執行（github.md §5）。

## 5 · 收尾檢查

- 七個核心概念的**最終值**已寫入，且與實際情況一致。
- 結案留言存在且含驗證結論；`## 裁定紀錄` 的索引指得到**審核階段確認**那則留言——授權在該次裁定取得（stages/審核.md §7）。
- 資源租用已釋放；狀態不明時標示「狀態未知」，下一位使用者⛔ 不得直接寫入（github.md §6）。
- 已確認經驗的正式落地、有效居所與新接手取讀，或明確承接卡及其實際結果已依 boundaries.md §7 登記；未確認候選仍是資料，缺漏⛔ 不假稱完成。
- **本卡專屬 PM 對話收尾**：任務結案、已授權後續操作與交接完成，且結案回報已保存後，停止本卡不再需要的一次性跟進，使用平台原生功能封存本卡專屬 PM 對話並保留紀錄；⛔ 不封存共同入口或仍承載其他未完成工作的對話，⛔ 不刪除紀錄。平台不支援或封存失敗時，在既有結案回報說明未完成項，⛔ 假稱已封存；⛔ 因此重開產品任務或新增批准關卡。
