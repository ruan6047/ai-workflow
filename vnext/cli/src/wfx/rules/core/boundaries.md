# 邊界

## 1 · 分層注入（四層）

規則依下列順序提供上下文，**後層只補充專案事實，⛔ 不複製或暗改前層規則**：

1. **框架核心**＝框架規則樹（本檔所在層）。
2. **使用者層**＝`~/.wf/`：跨專案的共同資料。
3. **專案層**＝該專案的 `.wf/`：專案補充與政策。
4. **任務層**＝Issue body 五章節＋七個核心概念＋該卡全部留言（原樣、⛔ 不分類）；規劃者與執行者另含本卡登記之相連卡的指定章節與已核定規劃（github.md §1）。

每段輸出帶來源標記，kind 四值對應四層。⛔ 不做 delta 合成、⛔ 不做模組層。角色、正式階段與研究子狀態各有獨立文件；純機械值域集中在 values.md。

## 2 · 使用者層的模型與工具資料

- **穩定**：模型使用說明——家族劃分、各自適合什麼、呼叫慣例。
- **短期**：模型可用性／額度備註——每則只記**來源與最後確認時間**。
- **跨專案工具經驗**：選用 `~/.wf/tool-usage.md`，記適用條件、來源與證據限制；單一專案慣例留專案層。僅載入明列的三檔，⛔ 不掃整個使用者目錄；工具檔缺席合法，⛔ 不改兩模型檔既有 `unknown` 語意。`--omit-user-layer` 必須在讀取前省略全部使用者層，首屏與附錄都不帶原文。

PM 派工前自行確認新鮮度並寫進派工內容；**過期或不確定即視為 unknown，照常派工但標明**。`unknown` 是備註文字，⛔ 不進值域、⛔ 不成為欄位。

⛔ 不建額度查詢、自動過期、TTL、重置時間計算或模型選擇引擎；工具⛔ 不判備註是否過期或缺欄。框架層⛔ 不得寫入任何具體模型名稱、額度數字或帳號狀態——前層⛔ 不得吞下後層資料。

## 3 · 專案層

採用專案只維護自己的 `.wf/`：專案政策（可含模型政策）與模組補充資料；框架本身也用 `.wf/` 提供自己的補充規則。專案政策⛔ 不得放帳號額度或時效資料。

⛔ 不為單一專案在框架內寫入耦合條文、欄位或分支——這類需求一律寫進該專案 `.wf/`。

**專案規範由專案自己指定**：在任一 `.wf/*.md` 用節名「專案規範」逐行宣告 `- <repo 相對路徑>：<要照做的工作>`。沒宣告的文件或工作⛔ 不算專案規範。

- 宣告的規範約束成果怎麼做，⛔ 不是新需求。派工怎麼帶入見 roles/PM.md §3；規劃、執行、審核怎麼對照見各階段文件。
- 規範之間、或規範與派工、其他專案文件衝突時，停下該項回報現象與證據（§6），⛔ 不自行擇一。
- 規範要求另外跑的檢查或占用的資源，仍照 stages/規劃.md §3 列為驗收外檢查。
- 宣告新增、更新或搬移時，由內容角色同步本體與直接引用並核對等同性；PM 機械複製宣告，受派內容角色讀適用本體。採用清單只檢查既有宣告格式、repo 相對路徑與目標可讀且非空及入口的明確機械片段，⛔ 不判語意正確、不執行入口或追讀任意外部連結；無機械形式時列定位與限制，交內容角色比對。經驗落地與退場照 §7。

**專案方向與短定位（本節是唯一定義）**：需求方確認的既有藍圖／方向文件保存專案目標、已裁定優先順序與非目標；方向應能讓人辨識服務誰／原問題、預期價值、支持成功的結果與證據。本體留原處，不重建或另養精簡副本。這些是內容用途，⛔ 不是固定章節、必填欄位或量化指標。藍圖⛔ 不是所有專案必備文件。

專案可在 `.wf/` 既有適當文件以一般文字短定位本體路徑、適用段落與需求方確認來源；本體已在 `.wf/` 時直接定位段落。⛔ 不要求固定檔名、節名格式、必填列項或設定鍵，也不以「專案規範」宣告方向；⛔ 不新增工具遞迴追讀或整本注入機制。

| 內容 | 權威與限制 |
|---|---|
| 專案方向 | 需求方確認的既有本體及引用原來源的後續有效裁定；需求方裁定目標、優先與非目標，PM 與共同協調只引用、登記及揭露衝突，⛔ 不自訂排序。 |
| 本卡成果與邊界 | 本卡 Issue 的需求、限制與非目標、驗收及適用裁定；需求階段承接適用內容，未承接的方向⛔ 不自動成為需求或驗收，方向更新⛔ 不自動修改已鎖定需求。 |
| 任務狀態 | GitHub Project 七個核心概念；事件與裁定依 github.md。方向本體、短定位與總覽⛔ 不複製狀態、完成度或占用。 |
| 技術規範 | 本節既有「專案規範」宣告所指本體；只約束怎麼做，⛔ 不因藍圖背景取得規範效力或新增成果。 |

藍圖混有流程、狀態或技術做法時，仍依各自權威生效，⛔ 不覆蓋框架公共規則或正式任務來源。舊藍圖只定位仍有效的方向段落，其餘標明歷史背景，⛔ 不把全文清理當任務前提。沒有藍圖、定位缺失、確認來源不可核實或內容已過時時，沿用本卡目標、有效裁定與限制處理不受影響部分；只在缺口實質影響本次成果、優先衝突或非目標判斷時，於既有需求活動補來源或裁定。無法辨識有效方向或與本卡裁定衝突時，只暫停受影響的判斷／操作並回報，⛔ 不自行選邊、不阻擋獨立任務；長期方向文件若成為另一主要成果，照既有入口另提有界工作。

**成果里程碑 [Milestone]（本節是唯一定義）**：使用者可辨識、可判定的分期成果；依需要在既有方向本體以自由文字或小表格說明所連目標／成功條件、使用者得到結果的範圍、本期必需與可延後內容，以及支持聲稱的最小成果證據。⛔ 不以卡數、全數關卡、合併或部署替代成果；⛔ 不是框架階段、任務群狀態或新的通關條件，沒有分期需求的單次任務直接使用本卡規劃，不硬湊內容。

需求方決定分期及價值／成本／風險取捨，受派內容角色判斷直接證據，將本卡承接部分列入原需求／規劃。需跨卡組合的成果證據，在已有合適承接卡的原需求／規劃中明示產生者、原交付位置及回看時機；真人判斷依既有規劃安排人工檢視。⛔ 不推給 PM 或不具名的未來角色；若是另一主要成果，沿原入口分流，⛔ 不附帶擴張小卡。

里程碑回看沿相關任務的原階段交付、結案或影響該成果的既有取捨事件，不每卡每階段同步整本。依原內容／審核結論，在本體留下有來源的產品結果敘述或只連原結論，⛔ 不複製任務進度。「已達成」「部分成立」「未驗證」「被替代」須附範圍與證據，都是內容敘述，⛔ 不新增流程狀態或固定值域；缺使用者成果證據時如實說未證實，取消或替代也不代表原目標達成。上位未證實不阻擋已完成自身範圍的小卡；本卡仍承接的組合驗收若缺證據，則是本卡未完成，⛔ 不以此界線略過。

**具體前置與四類關係（本節是唯一定義）**：只對實際影響本次工作的關係，說清「哪個消費操作需要哪個成果／契約／輸入／版本、理由、原證據與限制、最小解除條件」。依原材料可辨識即可，⛔ 不要求編號、固定欄位、依賴檔或圖。每項結論依來源說明事實、推論或未知；未知⛔ 不代表低風險，也不自動要求全案等待。

| 關係 | 實質限制及解除依據 |
|---|---|
| 技術必需 | 內容角色以研究／方案判定某操作缺指定契約或成果就不能正確完成；取得相符的指定版本及直接證據才解除該前置，⛔ 不以生產者整卡關閉、連線或口頭預告代替。 |
| 資料／外部前提 | 指定資料版本、權限、外部可用性或使用者操作等實質條件；原來源、用途與原授權可核實且所需輸入／結果就緒才解除，⛔ 不用合成樣本或舊資料冒充。 |
| 業務希望先後 | 需求方基於價值、成本或時效的交付取捨；引用適用裁定及理由，⛔ 不證明後項技術不可先做，也不因改排序新增範圍或資源授權。 |
| 共享資源互斥 | 內容角色判定指定共享寫入／整合操作的實際交集，共同協調安排次序；操作前查當前基準、占用、必要租用／授權及隔離證據。排程、空的時間欄⛔ 不是鎖，⛔ 不阻隔離實作。 |

前置契約／版本／結果的事實與證據仍住原交付或研究；消費者本卡的核定規劃只保存自身操作的前置、來源與解除方式，共同協調安排只保存操作次序及原來源。任務狀態、期限、目前占用與技術規範各沿本節原權威，⛔ 不另養進度表。相連卡自動帶入的內容仍僅供判斷歸屬（github.md §1、flow.md §2）；本卡需求／規劃先明確承接所需接口、資料及解除條件，再由本卡內容角色窄讀原交付／研究事實並留來源，⛔ 不把相連卡方案改作規劃輸入、不遞迴整本或接手他卡工作。

具體交付可解除其真正支持的操作，⛔ 不等生產者整卡：固定候選契約或樣本可依消費者原核定規劃展開隔離工作，須標明候選身份、固定版本識別、變動風險與使用限制。這不代表前置已驗收，⛔ 不免兩卡正式審核或准許未授權整合／資料操作；正式或不可逆操作仍核對真正需要的已核定版本與證據。只用候選物的演練⛔ 不宣稱正式契約或產品已成立。

假依賴或循環先由內容角色按具體操作拆解：業務排序、共享窗口、整卡關閉⛔ 不自行變成技術前置，也不反證隔離不成立。真契約互相依賴可提出固定接口、可替換樣本、先做一條端到端路徑或調整分工，仍受本卡核定邊界約束，⛔ 不自行改公開契約／別卡範圍。未知、版本失效或證據矛盾只停消費該前提的操作並回報；必要釐清沿 research.md 的有界問題及終點，方案缺陷沿原退回，方向／風險取捨交需求方（§6）。無關工作續行，⛔ 不建自動依賴圖、循環檢查器或全案重排。

**執行順序**先找能讓使用者取得可核對價值的一條端到端路徑 [End-to-end Path]，再增覆蓋或自動化；⛔ 不固定先做完全部底層，也不省略該成果必需的資料真實性、安全或契約。內容角色判斷串行／隔離並行，需求方裁定價值與成本／風險，共同協調只在既有交界事件安排有交集共享操作（PM-coordination.md §2）。已核定且無交集直接續行；預估／順序⛔ 不是期限、授權或鎖，即時窗口／占用在實際操作前查。

**方向改動生命週期**沿既有活動銜接，⛔ 不新增階段或固定批准：

- 任何角色可提出含現象、證據、受影響方向與建議處置的候選；提出⛔ 不等於生效。需求方在既有需求活動或裁定中決定，已有效決定的部分直接沿用，⛔ 不重問。建立／採用方式見 stages/需求.md §2。
- 方向取捨與直接引用只隨需求方實質改變目標／成果分期、裁定跨卡優先取捨、改變非目標，或新證據推翻前提且需求方已作決定而更新；日常開卡、進階段、完成、合併、環境故障、技術改法與新原因發現不單獨觸發。前述成果回看可依原結論更新有來源的結果敘述／連結，⛔ 不藉客觀事實改產品取捨或任務狀態。
- 受派內容角色依確認集合修改本體與直接引用，PM 忠實登記適用裁定，⛔ 不代改內容。保留原來源，以既有版本或來源連結說明哪些段落被哪項有效決定取代／停用及適用範圍，歷史材料⛔ 不再作目前指示；⛔ 不新增版本欄位或自動覆寫。
- 既有跨卡取捨事件的有界影響協調與各卡處置見 PM-coordination.md §2；只影響部分任務時不整批退回，本卡成果方向確需變更才照 flow.md §3 退回需求。方向排序⛔ 不證明技術相依或互斥，技術判斷仍交內容角色。

里程碑／前置／順序的變動亦沿上述候選、裁定與原成果來源處理。受派內容角色更新本體的成果取捨及直接引用，消費者內容角色更新本卡前置與原證據指標，原交付保留實際版本；PM 只登記。核定範圍內不違反依賴、不改風險／驗收的局部步驟調整依 stages/執行.md 說明即可，⛔ 不新增確認；新成本／新動作依 §6，成果方向變動依 flow.md §3。

| 變動 | 原位置的更新及局部處置 |
|---|---|
| 部分交付／外部延誤 | 內容角色指出已有證據的成果、缺條件的消費操作及最小解除；只停該操作，隔離工作及有效證據續用。改承諾／接受新風險才交原裁定。 |
| 縮減／取消 | 需求方決定保留／排除成果及剩餘問題，內容角色保留原來源並標明取代／停用範圍；成果方向改的卡退回需求、不做者走原停止，⛔ 不刪驗收冒充完成或批次退回。 |
| 替代／合併 | 指明接手的具體成果、接口／資料來源、證據可沿用範圍與殘留風險；消費者內容角色核對新前置。換卡號⛔ 不是等價或達成證據，未變契約不重跑完整流程。 |
| 插單／重排 | 需求方決定價值取捨，共同協調重排有交集操作；既定安排內無交集者續行，⛔ 不自動撤銷他卡授權或給新資料／部署權限。 |
| 版本／假設失效或矛盾 | 內容角色界定失效版本、消費者及證據；方案問題回本卡規劃，成果方向需改才回需求，審核失效範圍沿 flow.md §6／§8；⛔ 不沿用失效結果或重審無關成果。 |

新文字⛔ 不自動改正在執行卡的範圍；先停相關操作、保存成果與來源，再依原裁定／退回處理。原占用卡按 github.md §6 確認程序停止及必要恢復後處理釋放；未知如實登記、只停下一次相關寫入。排程取消⛔ 不等於鎖已釋放，⛔ 不刪他人資源或空等舊 PM；交接以 PM-coordination.md §3 的可核實停止證據及安全接手為準。

各階段使用本卡已承接的目標關係，依既有成果與直接證據區分本卡完成、對目標已證實的貢獻及上位未達成／未驗證部分；各自操作見 stages/需求.md、規劃.md、執行.md、審核.md、結案.md。上位未完全達成⛔ 不阻擋範圍已完成的小卡結案，⛔ 不自動產生追蹤任務、等待未來自然採用或追加驗收。

## 4 · CLI 邊界

CLI 只負責：

- 載入與呈現規則及必要清單；
- 保存與顯示合法的流程狀態；
- 檢查資料格式、必要章節存在且非空，以及 SHA、分支、CI 等客觀事實；
- 偵測過期寫入並拒絕覆寫。

CLI ⛔ 不負責：

- 判斷需求、研究、根因、風險、內容品質或模型能力；
- **呼叫、選擇或調度 AI**；
- 包含模型 provider、AI adapter、額度引擎或任意工作流規則引擎。

**內容判斷由人或負責該內容的 AI 完成。** 核心保存不透明任務識別、⛔ 不理解其格式、⛔ 不依賴平台專屬型別，平台細節住 adapter。框架以版本化套件提供，規則來源可用 `--rules-root` 指向含 `core/` 的 `rules/` 目錄本身（⛔ 不是 checkout 根目錄）。

三個 wfx 動詞不變。套件另隨附顯式呼叫的 `python -m wfx.codegraph` 專用伴隨入口，
只定位固定版 CodeGraph、檢查 opt-in／顯式路徑／自身圖、控制環境並傳遞固定 query/explore 的 argv 與原生輸出。
它是 `wfx.gh` 之外唯一允許啟動外部 CLI 的固定檔案 `wfx/codegraph.py`；核心與其他位置仍⛔ 不啟動子行程。
此入口⛔ 不安裝／管理索引、不調度 AI、不寫任務流程，不是任意命令代跑、純讀保證、沙箱或權限判斷器。

## 5 · 模組四禁

模組只能在固定擴充點注入**文件、輸入、命令或客觀檢查**，⛔ 不得新增正式階段、狀態、計數器或轉移規則，也⛔ 不得新增／刪除／改義／改值域七個核心概念。

要改變流程形狀時另立獨立需求，⛔ 不預建任意流程擴充能力。測試驅動開發等方法可作為選用模組，⛔ 不成為所有專案的核心義務。

### 本版契約：選用文件模組

四種擴充點中，本版**只實作「文件」**；輸入、命令、客觀檢查保留，待有直接使用證據時各自另立需求。
`codegraph` 是此文件契約的具體模組，另有上述專用 companion helper 與 `wfx/docs/CODEGRAPH.md` 集中指南；
這是明示的局部能力增量，⛔ 不是模組載入器的命令擴充點。文件載入與 helper 呼叫分開，⛔ 不擴為通用 runtime。

- **來源**：模組內容只住框架規則樹 `modules/<名稱>/<階段>.md`，隨框架套件發版；檔名就是生效的階段。專案層、使用者層與第三方⛔ 不提供模組內容。
- **啟用**：專案在 `.wf/config.json` 以 `"modules": ["<名稱>", …]` 宣告；啟用時清單非空，名稱不重複、不含路徑分隔。
- **停用**：缺鍵或 `null`＝停用；空清單 `[]` ⛔ 不是停用，是形狀錯；停用時 `brief` ⛔ 不注入任何模組內容（附錄無模組來源段、首屏無啟用模組定位段），同版同規則樹下輸出與未啟用設定一致。
- **生效**：`brief` 只注入已啟用模組中檔名等於當前階段的文件，依宣告順序附在適用規則之後，來源標記仍是 `framework`——⛔ 不是第五層、⛔ 不增動詞；生效只看階段，⛔ 不分角色。
- **無效設定**：`modules` 形狀不對（含 `[]`）＝`brief`、`write`、`facts --task` 都 `ConfigError`（rc 1）；`facts --adopt` 例外，列為「格式錯誤」、rc 0；名稱不在規則樹或目錄內沒有文件＝`brief` 的 `LayerMissing`（rc 1）；模組文件的檔名不是階段值＝`MalformedInput`（rc 1）。已啟用模組不論當前階段都會驗，⛔ 不靜默略過。

已知影響：新增或修改模組須隨框架套件發版；多個模組只依宣告順序並列，⛔ 無衝突偵測或合併。未知且未驗證：輸入、命令、客觀檢查三類的形狀，依角色生效的需要，以及多模組衝突——以第一個樣本⛔ 不得宣稱全面相容。

## 6 · 偏移、根因與停止

- **finding ⛔ 不能直接變成 patch。** 內容角色先說明使用者影響、證據、可能根因與唯一責任層，再決定修正位置。
- 優先移除末端例外並修正上游原因；⛔ 不得為一次失誤在多層新增重複守衛。
- 問題宣告解除並正式交付後，又在審核或後續正式交付中被證實存在，才算**同一根因再次發生**；此時停止繼續補洞，交需求方裁定。執行中的正常修正、測試失敗與測試重跑⛔ 不算。
- 發現者只回報現象、證據與影響。內容角色可以建議退回需求、退回規劃或停止；**PM ⛔ 不做技術裁決**。
- 可客觀確認的外部條件暫時不可用時，PM 可以標記阻塞。涉及方向、需求假設、風險接受或是否停止時，一律由需求方人工裁定。
- **偏離本卡主要成果的工作，做之前或派出之前先停下該項，交需求方決定。** 判準＝本卡 `## 需求` 的主要成果，⛔ 不以當輪派工、核定規劃或專案規則為準——它們要求、但偏離主要成果的工作仍算偏離。**已決定範圍**＝需求方已核定的需求，以及需求方已就該項明確決定過的工作（如規劃確認時保留的驗收外檢查，以規劃所寫的成本為限；已登記的需求方裁定）；PM 的派工允許⛔ 不等於需求方決定。範圍外的偏離工作在需求方決定前⛔ 不動手、⛔ 不派出，也⛔ 不成為執行完成、push 或送審的前提。停下的是該項，⛔ 不是整卡退回；決定改變成果方向時才照 flow.md §3 退回需求。一定要先停的四種：
  - **工具／環境失敗的排除**：成果本身以外的工具、驗證輔助、下載、網路、權限、外部站台或本機環境失敗時，診斷、改設定、換工具或路徑、寫繞道檔之前先停；選項＝排除、略過該項、停止。成果本身的實作或測試缺陷與原樣重跑照 stages/執行.md §4，⛔ 不算排除。
  - **需求方中途訊息衍生的新工作**：需求方的訊息（含提問）會變成新工作或超出主要成果時，先問要不要做，同意並登記（roles/PM.md §3）後才派。已明確裁定要做並已登記的照裁定派工，⛔ 不再問。
  - **已決定範圍外新加的檢查**：PM 派工（含修訂派工）自行點名加入、或規劃核定後才加入（含執行者自加）的檢查。規劃階段經需求方同意加入的，仍照 stages/規劃.md §3 列為驗收外檢查，⛔ 不寫成必做或不得豁免。
  - **已保留項目的實際成本超出規劃所寫**（如下載量、重跑輪數、協調授權次數）：交需求方重新決定保留或排除。
- **偏離工作誰停、怎麼問**：發現的角色停下，回報現象、證據、影響與預估排除成本；PM 當成需要裁定通知需求方（roles/PM.md §5），選項併成一個問句。判斷不出是否偏離時，當成偏離來問；PM 與內容角色⛔ 不自行裁定。
- **缺少證據不代表低風險。** 未知事項可能影響安全、資料、正式環境、公開契約或其他主要成果時，先安排釐清，再執行相關操作。

動作被拒後，由執行該動作的內容角色比對原授權與實際請求；來源未核實先核對可取得的原來源，有新增或未涵蓋的目的地、資料、版本或動作時，只交需求方補該實質缺口。來源不可取得而無法判定授權充分性時，回報證據不足與未能判斷之處，⛔ 不逕歸為已足仍拒。可核實且涵蓋同一請求的授權已足仍被平台拒絕時，保留原請求、拒絕理由與來源，標示可能平台授權辨識異常；⛔ 不重問已授權動作、不改寫目的或管道繞過拒絕。未知當次審查實收上下文時，⛔ 不斷言根因。

## 7 · 經驗的確認、落地與退場

**事件觸發與提報**：任何階段發現可供後續任務重用的新限制、同型失誤重現、操作事故或推翻舊內容的新事實時，由發現的內容角色主動提出來源、適用範圍、目前效力、建議居所與具體差異，交回本卡 PM；PM 或需求方先發現時，由 PM 交本卡適當的內容角色在允許階段提煉，⛔ 不以事故登記或本次修復代替。PM 將需確認的精確集合併入既有需裁定通知／階段確認，交需求方決定保留、更新、退場或不提升，⛔ 不等待需求方自行追問；收到確認後沿本節既有時點安排落地或明確承接。

只處理本次事件的可重用部分，⛔ 不要求每次交付填寫「無經驗」、不為每個 finding 新增規則或另開卡。既有注意事項已足以涵蓋時，指出原條文與執行偏差，修正執行及取讀缺口，不得另加同義禁令；需要修改正式文件時仍依本節確認與允許階段處理。未確認候選仍是資料，在既有交付／結案回報列出來源及尚未裁定部分，不冒稱已落地；候選不自動阻擋原交付，也不豁免本卡缺陷或已確認經驗的落地責任。

經驗先作卡片級資料；內容角色提出來源、適用範圍、目前效力、擬修改位置與具體差異。PM 可登記候選並建議歸屬，⛔ 不代提煉或代修正式文件。提升到專案層、使用者層或框架層前，由需求方確認擬寫集合；已確認值得保留的內容⛔ 不得再降為無主候選規避落地。

- **執行完成前確認**：研究／規劃階段的確認帶入同卡執行，由執行者隨本卡修改正式文件、自檢差異並驗證新接手讀得到；執行階段確認者同樣處理。不得只留候選或交給不具名的未來任務。
- **審核通過後才確認，屬使用者層且不影響專案受審 SHA**：可在原卡結束前由受派內容角色依需求方確認的精確集合受控落地；保留原文、存在性、權限與結果識別，確認未遇後續修改後逐檔套用，驗證取讀。PM 只協調與登記，不修改內容；不因這項本機經驗而讓已批准的產品 PR 退回重審。
- **審核通過後才確認，屬專案／框架 repository**：允許在原卡關卡前，以符合 flow.md §4 的已定案改動卡明確承接落地與取讀驗證；走既有共同入口查重與指派，列明承接卡、具體檔案／段落／逐字內容、既定驗證方式與受派責任，並在原卡登記來源及實際承接結果。⛔ 不只留無主候選，不將未完成的落地記為已完成；不為記錄這則經驗修改已批准產品 PR 的受審 SHA。條件未定案或影響原產品正確性的缺陷，仍照既有退回與裁定程序，不能用經驗承接規避。
- **審核尚未通過時**：需要改受審成果仍走既有退回；不能借本節直接改受審版本。

每一事實只維持一個有效權威居所，依 §1–§3 選層；宣告與派工引用原文，不另養可獨立演進的副本。新增、修改、搬移時同步有效居所、宣告及直接引用；搬移須比對本體，不能只換路徑。落地證據連起來源、需求方確認、正式差異、有效居所及新接手取讀；沒有自然後續任務時可作有界演練，明示不等於生產使用。

新事實推翻舊內容時，內容角色提出原地更新或退場集合，需求方確認後修改原有效居所與引用；有歷史價值者保留版本、時期、來源及限制，⛔ 不再作目前指示。模型名稱或入口更新不等於歷史能力觀察已更新；沒有新證據就明示未知，不補造能力、配額或成功率。未確認或證據不足內容仍是資料。

結案依本節核對各項已確認經驗的落地或明確承接及取讀證據；缺漏不得假稱完成。⛔ 不因每則經驗各開卡、不建編號體系、提升門檻、計數器或自動覆寫機制；獨立主要成果仍照既有共同入口與需求邊界處理。
