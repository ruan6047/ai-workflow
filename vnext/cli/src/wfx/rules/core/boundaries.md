# 邊界

## 1 · 分層注入（四層）

規則依下列順序提供上下文，**後層只補充專案事實，⛔ 不複製或暗改前層規則**：

1. **框架核心**＝框架規則樹（本檔所在層）。
2. **使用者層**＝`~/.wf/`：跨專案的共同資料。
3. **專案層**＝該專案的 `.wf/`：專案補充與政策。
4. **任務層**＝Issue body 五章節＋七個核心概念＋該卡全部留言（原樣、⛔ 不分類）；規劃者與執行者另含本卡登記之相連卡的指定章節與已核定規劃（github.md §1）。

每段輸出帶來源標記，kind 四值對應四層。⛔ 不做 delta 合成、⛔ 不做模組層。角色、正式階段與研究子狀態各有獨立文件；純機械值域集中在 values.md。

## 2 · 使用者層的模型與工具資料

- **穩定**：模型使用說明——家族劃分、各自適合什麼、呼叫慣例。
- **短期**：模型可用性／額度備註——每則只記**來源與最後確認時間**。
- **跨專案工具經驗**：選用 `~/.wf/tool-usage.md`，記適用條件、來源與證據限制；單一專案慣例留專案層。僅載入明列的三檔，⛔ 不掃整個使用者目錄；工具檔缺席合法，⛔ 不改兩模型檔既有 `unknown` 語意。`--omit-user-layer` 必須在讀取前省略全部使用者層，首屏與附錄都不帶原文。

PM 派工前自行確認新鮮度並寫進派工內容；**過期或不確定即視為 unknown，照常派工但標明**。`unknown` 是備註文字，⛔ 不進值域、⛔ 不成為欄位。

⛔ 不建額度查詢、自動過期、TTL、重置時間計算或模型選擇引擎；工具⛔ 不判備註是否過期或缺欄。框架層⛔ 不得寫入任何具體模型名稱、額度數字或帳號狀態——前層⛔ 不得吞下後層資料。

## 3 · 專案層

採用專案只維護自己的 `.wf/`：專案政策（可含模型政策）與模組補充資料；框架本身也用 `.wf/` 提供自己的補充規則。專案政策⛔ 不得放帳號額度或時效資料。

⛔ 不為單一專案在框架內寫入耦合條文、欄位或分支——這類需求一律寫進該專案 `.wf/`。

**專案規範由專案自己指定**：在任一 `.wf/*.md` 用節名「專案規範」逐行宣告 `- <repo 相對路徑>：<要照做的工作>`。沒宣告的文件或工作⛔ 不算專案規範。

- 宣告的規範約束成果怎麼做，⛔ 不是新需求。派工怎麼帶入見 roles/PM.md §3；規劃、執行、審核怎麼對照見各階段文件。
- 規範之間、或規範與派工、其他專案文件衝突時，停下該項回報現象與證據（§6），⛔ 不自行擇一。
- 規範要求另外跑的檢查或占用的資源，仍照 stages/規劃.md §3 列為驗收外檢查。
- 宣告新增、更新或搬移時，由內容角色同步本體與直接引用並核對等同性；PM 機械複製宣告，受派內容角色讀適用本體。採用清單只檢查既有宣告格式、repo 相對路徑與目標可讀且非空及入口的明確機械片段，⛔ 不判語意正確、不執行入口或追讀任意外部連結；無機械形式時列定位與限制，交內容角色比對。經驗落地與退場照 §7。

## 4 · CLI 邊界

CLI 只負責：

- 載入與呈現規則及必要清單；
- 保存與顯示合法的流程狀態；
- 檢查資料格式、必要章節存在且非空，以及 SHA、分支、CI 等客觀事實；
- 偵測過期寫入並拒絕覆寫。

CLI ⛔ 不負責：

- 判斷需求、研究、根因、風險、內容品質或模型能力；
- **呼叫、選擇或調度 AI**；
- 包含模型 provider、AI adapter、額度引擎或任意工作流規則引擎。

**內容判斷由人或負責該內容的 AI 完成。** 核心保存不透明任務識別、⛔ 不理解其格式、⛔ 不依賴平台專屬型別，平台細節住 adapter。框架以版本化套件提供，規則來源可用 `--rules-root` 指向含 `core/` 的 `rules/` 目錄本身（⛔ 不是 checkout 根目錄）。

## 5 · 模組四禁

模組只能在固定擴充點注入**文件、輸入、命令或客觀檢查**，⛔ 不得新增正式階段、狀態、計數器或轉移規則，也⛔ 不得新增／刪除／改義／改值域七個核心概念。

要改變流程形狀時另立獨立需求，⛔ 不預建任意流程擴充能力。測試驅動開發等方法可作為選用模組，⛔ 不成為所有專案的核心義務。

### 本版契約：選用文件模組

四種擴充點中，本版**只實作「文件」**；輸入、命令、客觀檢查保留，待有直接使用證據時各自另立需求。

- **來源**：模組內容只住框架規則樹 `modules/<名稱>/<階段>.md`，隨框架套件發版；檔名就是生效的階段。專案層、使用者層與第三方⛔ 不提供模組內容。
- **啟用**：專案在 `.wf/config.json` 以 `"modules": ["<名稱>", …]` 宣告；啟用時清單非空，名稱不重複、不含路徑分隔。
- **停用**：缺鍵或 `null`＝停用；空清單 `[]` ⛔ 不是停用，是形狀錯；停用時 `brief` ⛔ 不注入任何模組內容（附錄無模組來源段、首屏無啟用模組定位段），同版同規則樹下輸出與未啟用設定一致。
- **生效**：`brief` 只注入已啟用模組中檔名等於當前階段的文件，依宣告順序附在適用規則之後，來源標記仍是 `framework`——⛔ 不是第五層、⛔ 不增動詞；生效只看階段，⛔ 不分角色。
- **無效設定**：`modules` 形狀不對（含 `[]`）＝`brief`、`write`、`facts --task` 都 `ConfigError`（rc 1）；`facts --adopt` 例外，列為「格式錯誤」、rc 0；名稱不在規則樹或目錄內沒有文件＝`brief` 的 `LayerMissing`（rc 1）；模組文件的檔名不是階段值＝`MalformedInput`（rc 1）。已啟用模組不論當前階段都會驗，⛔ 不靜默略過。

已知影響：新增或修改模組須隨框架套件發版；多個模組只依宣告順序並列，⛔ 無衝突偵測或合併。未知且未驗證：輸入、命令、客觀檢查三類的形狀，依角色生效的需要，以及多模組衝突——以第一個樣本⛔ 不得宣稱全面相容。

## 6 · 偏移、根因與停止

- **finding ⛔ 不能直接變成 patch。** 內容角色先說明使用者影響、證據、可能根因與唯一責任層，再決定修正位置。
- 優先移除末端例外並修正上游原因；⛔ 不得為一次失誤在多層新增重複守衛。
- 問題宣告解除並正式交付後，又在審核或後續正式交付中被證實存在，才算**同一根因再次發生**；此時停止繼續補洞，交需求方裁定。執行中的正常修正、測試失敗與測試重跑⛔ 不算。
- 發現者只回報現象、證據與影響。內容角色可以建議退回需求、退回規劃或停止；**PM ⛔ 不做技術裁決**。
- 可客觀確認的外部條件暫時不可用時，PM 可以標記阻塞。涉及方向、需求假設、風險接受或是否停止時，一律由需求方人工裁定。
- **偏離本卡主要成果的工作，做之前或派出之前先停下該項，交需求方決定。** 判準＝本卡 `## 需求` 的主要成果，⛔ 不以當輪派工、核定規劃或專案規則為準——它們要求、但偏離主要成果的工作仍算偏離。**已決定範圍**＝需求方已核定的需求，以及需求方已就該項明確決定過的工作（如規劃確認時保留的驗收外檢查，以規劃所寫的成本為限；已登記的需求方裁定）；PM 的派工允許⛔ 不等於需求方決定。範圍外的偏離工作在需求方決定前⛔ 不動手、⛔ 不派出，也⛔ 不成為執行完成、push 或送審的前提。停下的是該項，⛔ 不是整卡退回；決定改變成果方向時才照 flow.md §3 退回需求。一定要先停的四種：
  - **工具／環境失敗的排除**：成果本身以外的工具、驗證輔助、下載、網路、權限、外部站台或本機環境失敗時，診斷、改設定、換工具或路徑、寫繞道檔之前先停；選項＝排除、略過該項、停止。成果本身的實作或測試缺陷與原樣重跑照 stages/執行.md §4，⛔ 不算排除。
  - **需求方中途訊息衍生的新工作**：需求方的訊息（含提問）會變成新工作或超出主要成果時，先問要不要做，同意並登記（roles/PM.md §3）後才派。已明確裁定要做並已登記的照裁定派工，⛔ 不再問。
  - **已決定範圍外新加的檢查**：PM 派工（含修訂派工）自行點名加入、或規劃核定後才加入（含執行者自加）的檢查。規劃階段經需求方同意加入的，仍照 stages/規劃.md §3 列為驗收外檢查，⛔ 不寫成必做或不得豁免。
  - **已保留項目的實際成本超出規劃所寫**（如下載量、重跑輪數、協調授權次數）：交需求方重新決定保留或排除。
- **偏離工作誰停、怎麼問**：發現的角色停下，回報現象、證據、影響與預估排除成本；PM 當成需要裁定通知需求方（roles/PM.md §5），選項併成一個問句。判斷不出是否偏離時，當成偏離來問；PM 與內容角色⛔ 不自行裁定。
- **缺少證據不代表低風險。** 未知事項可能影響安全、資料、正式環境、公開契約或其他主要成果時，先安排釐清，再執行相關操作。

動作被拒後，由執行該動作的內容角色比對原授權與實際請求；來源未核實先核對可取得的原來源，有新增或未涵蓋的目的地、資料、版本或動作時，只交需求方補該實質缺口。來源不可取得而無法判定授權充分性時，回報證據不足與未能判斷之處，⛔ 不逕歸為已足仍拒。可核實且涵蓋同一請求的授權已足仍被平台拒絕時，保留原請求、拒絕理由與來源，標示可能平台授權辨識異常；⛔ 不重問已授權動作、不改寫目的或管道繞過拒絕。未知當次審查實收上下文時，⛔ 不斷言根因。

## 7 · 經驗的確認、落地與退場

經驗先作卡片級資料；內容角色提出來源、適用範圍、目前效力、擬修改位置與具體差異。PM 可登記候選並建議歸屬，⛔ 不代提煉或代修正式文件。提升到專案層、使用者層或框架層前，由需求方確認擬寫集合；已確認值得保留的內容⛔ 不得再降為無主候選規避落地。

- **執行完成前確認**：研究／規劃階段的確認帶入同卡執行，由執行者隨本卡修改正式文件、自檢差異並驗證新接手讀得到；執行階段確認者同樣處理。不得只留候選或交給不具名的未來任務。
- **審核通過後才確認，屬使用者層且不影響專案受審 SHA**：可在原卡結束前由受派內容角色依需求方確認的精確集合受控落地；保留原文、存在性、權限與結果識別，確認未遇後續修改後逐檔套用，驗證取讀。PM 只協調與登記，不修改內容；不因這項本機經驗而讓已批准的產品 PR 退回重審。
- **審核通過後才確認，屬專案／框架 repository**：允許在原卡關卡前，以符合 flow.md §4 的已定案改動卡明確承接落地與取讀驗證；走既有共同入口查重與指派，列明承接卡、具體檔案／段落／逐字內容、既定驗證方式與受派責任，並在原卡登記來源及實際承接結果。⛔ 不只留無主候選，不將未完成的落地記為已完成；不為記錄這則經驗修改已批准產品 PR 的受審 SHA。條件未定案或影響原產品正確性的缺陷，仍照既有退回與裁定程序，不能用經驗承接規避。
- **審核尚未通過時**：需要改受審成果仍走既有退回；不能借本節直接改受審版本。

每一事實只維持一個有效權威居所，依 §1–§3 選層；宣告與派工引用原文，不另養可獨立演進的副本。新增、修改、搬移時同步有效居所、宣告及直接引用；搬移須比對本體，不能只換路徑。落地證據連起來源、需求方確認、正式差異、有效居所及新接手取讀；沒有自然後續任務時可作有界演練，明示不等於生產使用。

新事實推翻舊內容時，內容角色提出原地更新或退場集合，需求方確認後修改原有效居所與引用；有歷史價值者保留版本、時期、來源及限制，⛔ 不再作目前指示。模型名稱或入口更新不等於歷史能力觀察已更新；沒有新證據就明示未知，不補造能力、配額或成功率。未確認或證據不足內容仍是資料。

結案依本節核對各項已確認經驗的落地或明確承接及取讀證據；缺漏不得假稱完成。⛔ 不因每則經驗各開卡、不建編號體系、提升門檻、計數器或自動覆寫機制；獨立主要成果仍照既有共同入口與需求邊界處理。
