# 流程

## 1 · 為什麼有這個流程

框架要讓採用它的專案更快、更省心地交付可靠成果。核心目標是在昂貴實作前攔住**錯誤方向、錯誤假設與跨階段越權**；成果必須**正確、容易檢視、可重現且可追溯**。

**流程成本與任務風險相稱**；⛔ 不再要求量化證明使用框架比需求方直接管理 AI 更快、更省時間與心力。依**實際發生**的情境檢查，沒有發生的錯誤⛔ 不要求刻意製造；⛔ 不得產生沒有決策用途的文件、數據與驗證。

多階段、多角色與多模型只是在能改善這些結果時使用的手段，不是目的。⛔ 不得為單次失誤、推測風險或未出現的使用情境建立大型機制。

## 2 · 五個階段

正式流程只有五個階段，線性推進：**需求 → 規劃 → 執行 → 審核 → 結案**。

- 研究是需求或規劃內的**選用子狀態**，不是階段（見 research.md）。
- **部署與維護是任務類型，不是階段。** ⛔ 不得為它們新增階段、狀態、看板或欄位。
- 一張任務卡只有一個主要成果，並指定一位最終需求方。含兩個主要成果時拆成**相連任務**，彼此以 issue 連結標明。
- 任務大小依主要產物切分：程式碼任務聚焦一個行為、文件任務聚焦一個讀者目的、設計任務聚焦一個決策、研究任務聚焦一個問題。**行數只作警示**，超量時說明合理性，⛔ 不作硬性拒收。
- 緊急性只影響排程，⛔ 不降低需求確認、執行自檢、獨立審核或結案證據要求。

各階段怎麼做住 `stages/`；角色責任住 `roles/`；值域住 values.md。

## 3 · 需求鎖定

需求核定後鎖定成果方向。後續階段⛔ 不得自行改變成果、需求邊界、公開契約、主要驗收或已接受風險。

**方向改動一律停止目前階段、退回需求階段，由需求方人工裁定。**

## 4 · 階段確認

- **需求、規劃、執行、審核四個正式階段**完成時由需求方確認；一次確認只呈現**一個畫面**的成果、疑慮與下一步。結案⛔ 不另設批准（§8）。
- **討論一次只處理一個問題。** 階段結束時 PM 先提供一個畫面讀得完的決策摘要，再用**一個明確問句**請需求方確認：「是否接受本階段成果並進入〈下一階段〉？有補充或疑慮請在同一則回覆提出。」審核階段的問句同時列明已知的合併、部署或外部變更授權（stages/審核.md §7）。
- 明確接受（含對此問句回覆「好／OK」）即確認本階段，同一回覆附帶的補充或疑慮仍要處理；回覆只有疑慮而未表示接受時，本階段尚未確認，PM 處理疑慮後再提出同一個問句。需求方隨時可以提出疑慮。此確認⛔ 不等於人工正式審核者本人寫出的審核結果（stages/審核.md §5）。
- 一般研究的子狀態（高難度研究的例外見 research.md §6）、正常實作修正、測試重跑、非阻擋觀察⛔ 都不增加獨立確認點。
- 非阻擋觀察放在該次階段完成卡的固定小節，⛔ 不另發留言，也⛔ 不阻止階段完成。
- 合法退回後，被退回的階段必須重新完成並重新確認——**這不是增生**。增生＝無退回情況下同一階段出現第二次確認，或以子階段為主題的確認。
- 一個畫面裝不下時在該次確認回報，由需求方決定呈現方式，⛔ 不拆新卡、⛔ 不增加確認次數。

## 5 · 階段證據原則

- 一項驗收提供足以支持結論的**最小證據集合**；「一份結果」不是「只能有一個測試」。
- **任一階段的驗收證據，只能由該階段結束前已經存在的活動產生。** 執行階段的驗收⛔ 不得以審核或結案階段的活動為前提。
- **也不得以尚未建成的工具為前提。** 工具尚未存在時留下的紀錄是 **bootstrap**：如實標示、保留原樣，⛔ 不得事後重貼或改寫成「由工具產生」。
- 審核階段只核對交付當下受審版本（程式成果為 SHA）上已存在的事實。
- 規劃者與獨立審核者⛔ 不得被要求在執行階段提前交付；執行者自檢在執行階段，正式審核集中在審核階段。
- **數量⛔ 不代表品質**：文件、測試、量測及留言的數量都不是品質指標；證據只需支援關鍵判斷與成果重現。
- 一般風險任務沿用既有任務紀錄；只有內容需要**長期維護、重複使用或影響後續決策**時，才建立獨立文件。
- 首次採用可安排**少量、有界且事先說明目的**的演練，但⛔ 不得混入一般產品任務、⛔ 不得刻意製造問題來證明框架有效。

## 6 · 審核結果與退回

審核結果只有四種：**批准／退回執行／退回規劃／退回需求**。環境或權限不足使用本流程既有的阻塞狀態，⛔ 不新增專用狀態。再次審核只檢查先前阻擋項及其相關回歸。

**退回是事件，不是狀態。** 一次退回＝三個動作：

1. 階段改回需求／規劃／執行其一；
2. 狀態設 `待辦` 或 `進行中`；
3. 留一則含原因與證據的留言。

CLI 只檢查值在值域內，⛔ 不判退回是否合法、⛔ 不建轉移表、⛔ 不把三動作封裝成原子命令、⛔ 不要求欄位改動與留言成對出現。

`iteration` 只識別一次執行嘗試，⛔ 不作升級計數器。退回次數由既有事件歷史（階段欄變更與留言）由人推導，⛔ 不新增欄位、計數器或自動升級。

## 7 · 工作包

工作包＝已核定規劃內的有界交付單位，有邊界、依賴與可檢查證據。工作包⛔ 不是任務卡、⛔ 不進 Project、⛔ 不是子階段、⛔ 不是獨立確認點、⛔ 不各自被退回。**退回的最小粒度是整張任務卡。**

| 工作包可以 | 工作包不可以 |
|---|---|
| 調整相鄰測試、共用函式、必要實作位置 | 改變成果方向 |
| 修正規劃範圍內、可理解的實作或測試缺陷 | 改變公開契約 |
| 重跑測試（不算流程退回） | 改變主要技術 |
| 在不違反依賴下調整執行順序 | 改變風險、已接受風險、驗收或資源需求 |
| 回報現象、證據與影響 | 新增工作包以外的交付項、擴張需求邊界 |

任一「不可以」被觸發 ⇒ 停止當前階段，整卡退回需求。

## 8 · 結案的固定序

PM 整理結案卡 → **核對審核階段確認已授權的合併動作**（stages/審核.md §7）→ PM 合併 → 驗證合併結果（合併目標分支，一般為 `main`；CI 與正式成果）→ 驗證結論寫進**同一則**結案留言 → 關閉任務並完成必要清理。⛔ 不為此新增例行確認點。

**結案只執行已授權動作並回報實際結果，⛔ 不另設批准。** 授權只涵蓋審核確認當下已知的動作；**未涵蓋的新動作須在發生前取得需求方授權**。

**結案階段⛔ 不修改成果內容。** 開下一張卡、關閉本卡是平台協調操作，不是成果內容。

合併後失敗與本次成果有關 ⇒ 原卡不得結案：PM 標記阻塞，修正或回滾一律**退回執行階段**處理，再重新經過審核與結案。只有確認失敗與本次成果無關才可另開任務處理，且原卡仍須具備自己的完成證據。
