# TDD 選用模組：審核

讀者＝**審核者**。本文件只是核對指引：判準仍只有**已核定的需求與規劃**（審核階段 §2、§3），本模組⛔ 不是退回理由，也⛔ 不新增驗收標準。

## 1 · 看什麼

每個行為變更應有「先失敗（Red）、後通過（Green）」的證據，或一句不適用的理由。證據以 focused test（針對這次行為變更、可單獨重跑的測試）為準，並寫明 Green 之後有沒有 Refactor：有就附同一 focused test 重跑仍通過的輸出，沒有就附「未執行」與理由。

- **適用**：可觀察的行為變更，且專案現有的測試方式能先寫出預期結果。
- **不適用**（舉例）：純文件、不改行為的重構、可拋棄探針、需要人親自判斷的呈現、專案沒有可用的測試方式、只改測試（tests-only）、無行為的靜態設定、純統計結論——但同卡改了可觀察的 production 推論行為時，該部分仍適用。混合型任務只看行為部分。

## 2 · 怎麼核對與必要重現

先依審核階段 §2 核對執行者交付的 focused test、命令、base、實際受測版本及原始關鍵輸出：

1. 受審 exact SHA 的 focused test 通過證據；Green 後有 Refactor 時，核對同一 focused test 再次通過的證據，沒有則核對「未執行」與理由。
2. 所述 base 上只套用測試變更、因所述預期原因失敗的證據；語法錯誤，以及測試收集（collection）、import、設定（config）錯誤都不算 Red。

證據充分且仍有效時不預設重跑以上兩步；沿用原 Red 或其他未受影響結果時，保留原版本、輸出來源與沿用理由，核對測試、行為契約及相依是否已變。模組執行指引對適用行為變更要求的受審版本 Green 與 Refactor 後輸出仍由執行者交付，⛔ 以一般沿用條文豁免。

缺漏、矛盾、來源不明、變更使證據失效，或資料、安全及已核定契約風險需要釐清時，才針對必要的一步或兩步獨立重現；在受審 exact SHA 上重現 Green，在所述 base 上只套測試變更重現 Red。查核範圍依審核階段 §2、§6，不自動擴為全量測試；規劃或適用規範明定的審核查核仍須完成。重現不能倒證作者實作前確曾觀察 Red，⛔ 補造工作順序證據。

⛔ 不依賴提交順序；證據品質由你判斷，工具⛔ 不判斷。⛔ 不設 coverage（覆蓋率）門檻，也⛔ 不以 coverage 判斷 TDD 是否成立。

## 3 · 缺少證據時怎麼判斷

- **先核對直接證據，必要時才重現**：差異裡有覆蓋行為變更的測試，依 §2 核對來源、版本、失敗原因與通過結果；現有證據不足以判斷時，針對疑點作必要重現。核對成立、只缺文字說明＝記為觀察；審核者補得的重現證據⛔ 冒作執行者已交付或實作前曾觀察 Red 的證據。規劃明列但執行者未完成的測試或直接證據，仍依下一項處理。
- **可歸入既有理由時照常退回執行**：
  - 規劃要求的測試或直接證據不足——包括規劃已明列 TDD 證據，交付卻沒有；
  - 交付說明與事實不符，例如宣稱先失敗，但在 base 上重現是通過；
  - 適用的行為變更完全沒有測試，使規劃要求的回歸無法成立。
- **其餘情況**（證據薄弱、沒說明為何不適用、你認為應適用但規劃沒要求）：記為觀察，寫在該次階段完成卡內（flow.md §4），⛔ 不作退回理由。

專案 `.wf/` 要求 TDD 時，規劃者照 stages/規劃.md §3 處理：對得上驗收就列為直接證據，對不上就列為驗收外檢查，由需求方決定保留或排除。
