# TDD 選用模組：審核

讀者＝**審核者**。本文件只是核對指引：判準仍只有**已核定的需求與規劃**（審核階段 §3），本模組⛔ 不是退回理由，也⛔ 不新增驗收標準。

## 1 · 看什麼

每個行為變更應有「先失敗、後通過」的證據，或一句不適用的理由。

- **適用**：可觀察的行為變更，且專案現有的測試方式能先寫出預期結果。
- **不適用**（舉例）：純文件、不改行為的重構、可拋棄探針、需要人親自判斷的呈現、專案沒有可用的測試方式。混合型任務只看行為部分。

## 2 · 怎麼重現

1. 在受審 exact SHA 上執行所述測試，應通過。
2. 在所述 base 上只套用測試的變更，應因所述原因失敗。

⛔ 不依賴提交順序；證據品質由你判斷，工具⛔ 不判斷。

## 3 · 缺少證據時怎麼判斷

- **能自己重現就先重現**：差異裡有覆蓋行為變更的測試，照 §2 核對。核對成立、只缺文字說明＝記為觀察。
- **可歸入既有理由時照常退回執行**：
  - 規劃要求的測試或直接證據不足——包括規劃已明列 TDD 證據，交付卻沒有；
  - 交付說明與事實不符，例如宣稱先失敗，但在 base 上重現是通過；
  - 適用的行為變更完全沒有測試，使規劃要求的回歸無法成立。
- **其餘情況**（證據薄弱、沒說明為何不適用、你認為應適用但規劃沒要求）：記為觀察，寫在審核結果的非阻擋小節。

專案要把 TDD 證據變成硬性要求，正確路徑是寫進專案 `.wf/` 政策，再由規劃者寫進該卡規劃；之後缺少證據就是上面「規劃要求的測試或直接證據不足」。
