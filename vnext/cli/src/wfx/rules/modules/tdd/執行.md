# TDD 選用模組：執行

讀者＝**執行者**。本文件只是指引：啟用模組⛔ 不代表每張卡都要用 TDD，也⛔ 不新增交付門檻或交回格式。是否適用由你判斷，CLI ⛔ 不判斷。

## 1 · 何時適用

- **適用**：可觀察的行為變更，且專案現有的測試方式能先寫出預期結果。
- **不適用**（舉例）：純文件、不改行為的重構、可拋棄探針、需要人親自判斷的呈現、專案沒有可用的測試方式、只改測試（tests-only）、無行為的靜態設定、純統計結論——但同卡改了可觀察的 production 推論行為時，該部分仍適用。
- 混合型任務只對其中的**行為部分**套用。

## 2 · 在核定規劃內做

⛔ 不因本模組改變驗收、範圍或主要技術，也⛔ 不引入新的測試框架。需要新的測試基礎設施，或與規劃衝突時，依執行階段 §5 回報現象、證據與影響。

⛔ 不設 coverage（覆蓋率）門檻，也⛔ 不以 coverage 判斷 TDD 是否成立。

## 3 · 先失敗、後通過

1. 先寫 focused test（針對這次行為變更、可單獨重跑的測試），確認它**因預期的原因**失敗（Red）——語法錯誤，以及測試收集（collection）、import、設定（config）錯誤都不算 Red。
2. 再實作，確認同一 focused test 通過（Green）。

沒有先觀察到失敗，就如實寫出來；⛔ 不得補造或改寫證據。

## 4 · Green 之後才 Refactor

- Refactor 只在 Green 之後做；有 refactor 就重跑同一 focused test，確認仍通過。
- 不需要 refactor 時可以不做，寫明「未執行」與一句理由。

這是工作順序；證據是重跑的輸出，⛔ 不要求分 commit，也⛔ 不以提交時序證明先後。

## 5 · 交付說明寫什麼

寫進既有交付說明的自檢第 2 項，用一般文字，⛔ 不另定格式、⛔ 不另建文件。

- **適用時**：focused test 的位置與可重跑的命令、失敗時針對的 base 與關鍵輸出、在受審 exact SHA 上通過的輸出，以及 Refactor 後同一 focused test 的通過輸出，或「未執行」與理由。
- **不適用時**：一句理由，以及改用哪些既有證據。
