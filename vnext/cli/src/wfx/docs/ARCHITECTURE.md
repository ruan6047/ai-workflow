# 專案架構參考指南

本指南隨套件出貨，由內容角色按需讀取；`brief` 不自動追讀或注入本檔。
本檔集中說明選用 `architecture` 文件模組的用法，不另立權威層、角色、批准活動或機器狀態；原規則仍以 `rules/core/boundaries.md` §3／§5／§6／§7、`core/flow.md` 及適用階段為準。

## 1 · 用途與分工

架構參考讓任務理解元件責任、介面及資料流，配合藍圖判斷工作是否支援原主要成果；一張圖或啟用模組本身不能證明已防止偏軸。

| 來源 | 回答什麼／限制 |
|---|---|
| 需求方確認的藍圖 | 服務對象、價值、目標、優先與不做事項；技術事實不能自行改寫方向。 |
| 專案架構原本體及有效決策 | 元件責任、介面、資料流、寫入／部署邊界及取捨原因；效力依 §2 與原來源，不由文件名稱決定。 |
| CodeGraph／原始碼／設定 | 特定版本的程式現況證據；可達路徑不代表允許的責任、權限或期望架構。 |
| 本卡正式來源 | 本次成果、範圍、驗收與授權；架構資料不自動增加交付。 |

本模組與 CodeGraph 獨立：不需要安裝、啟用或索引即可使用架構文件，也可只用原始碼與既有契約。
需要工具時沿原 CodeGraph 模組與 [CODEGRAPH.md](CODEGRAPH.md) 操作；本指南不另定工具命令、權限或新鮮度政策。

## 2 · 分清內容效力

同一份架構文件可以混有下列內容，引用時說清適用段落、版本、來源及限制即可；這些是內容描述，不是新欄位、必填標記或六種正式狀態。

| 內容 | 如何使用 |
|---|---|
| 已驗現況 | 由原始碼、設定或交付版本支持；描述目前如何運作，不因存在而成為應遵守的規範。 |
| 有效決策／約束 | 連回仍適用的原決策；要作為專案技術規範，依 `core/boundaries.md` §3 的既有「專案規範」宣告，不將整本架構一律規範化。 |
| 已核定目標 | 指出核定來源及尚未實現的部分；不假稱現況已達成，也不自動擴張已鎖定任務。 |
| 候選或未知 | 只作取捨資料，不當既定需求或驗收。 |
| 歷史 | 保留適用時期／版本及被取代來源，不當目前指示。 |
| 例外 | 必須可核對原有效裁定、適用範圍與限制；歷史技術債不自動合法化。 |

任務、方向、技術規範與流程的權威仍各依原規則；不能因架構圖、工具結果或最新文件聲稱就自行選邊。任務狀態仍住 GitHub Project，不複製到架構文件。

## 3 · 初次建立與接入

先重用既有文件、圖、契約、原始碼與原決策，按已授權成果補足需要的內容；可涵蓋主要元件／資料流、責任／介面、寫入與部署權責，以及重要取捨的原因。
這些是內容用途，不要求固定檔名、章節、圖法、架構決策紀錄 [Architecture Decision Record, ADR] 或每元件一份文件；已有 ADR 就引用原文，沒有也可引用核定方案與裁定。

原本體留原處，沿 `.wf/` 既有適當文件提供路徑與適用段落，附可核對來源；這不是工具自動追讀指令，也不另養精簡副本。
其中確實約束做法的部分才按既有「專案規範」宣告，以原段落界定適用範圍；不要將背景、候選或歷史一併升格。

沒有架構本體的小專案或單次任務仍合法，不附帶要求先建文件。缺口實質影響本次成果才在原活動補必要來源；建立完整架構若已是另一主要成果，走既有共同入口分流。

## 4 · 任務使用與必要更新

新增模組、改變跨模組介面、資料流、寫入或部署責任，是按需查閱相關架構的線索；跨目錄本身不等於架構邊界改變，不觸發全庫掃描或全文閱讀。

規劃者沿用仍有效的決策，確實改變邊界時，在原規劃指明適用原文、取捨、受影響段落與必要文件交付；派工忠實承接，不另設文件批准或每卡固定驗收。
執行者隨核定交付更新已承接且確實失效的原段落與直接引用，審核者只核對本次影響、適用約束及證據。未預見且超出原範圍的架構改變，先依 §5 回報，不以「文件維護」隱含採用新邊界。

日常提交、局部改法、流程狀態或暫時環境故障，不是更新全圖或改變方向的理由。架構決策的原因及已接受取捨保留原來源；文件搬移／取代依 `core/boundaries.md` §7 同步本體與直接引用，不只換連結。

## 5 · 矛盾、過時與停止範圍

發現程式與文件不一致時，內容角色先列來源、版本、差異、影響與哪項操作受阻；不自行選邊、不自行採用例外，PM 不作技術裁決。處置依原規則，不因「架構」二字新增退回種類：

- 範圍內可理解的實作缺陷，由執行者依 `stages/執行.md` §1／§4 修正；正式審核發現缺陷則依 `stages/審核.md` 原結果處理。
- 方案前提失效而需重規劃，依 `core/boundaries.md` §3 與 `stages/執行.md` §5 回規劃；不是所有架構衝突都退需求。
- 成果方向或需求邊界需改，或觸發 `core/flow.md` §7 的不可以清單，按原規則停止當前階段、整卡退需求，不以局部調整繞過。
- 只有導覽過時或與本卡無關的歷史差異，說明失效段落／版本及限制，窄核本次必要原來源；不藉此整治全部技術債，也不自行認定為已核准例外。
- 證據不足時如實列未知，只停受影響操作；缺口影響主要成果、資料或安全時，依原規則釐清，不能假稱非阻擋。若另需一項成果，交原入口承接，不交給無名未來工作。

不受影響工作與仍有效證據續用，不因架構文件或 CodeGraph 缺席阻塞整張獨立任務。

## 6 · 三個使用情境

| 情境 | 依本指南及原規則處理 |
|---|---|
| 來源鏈問題轉向修本機休眠 | 先看原主要成果與有效方向，再定位資料產生／交付／供應責任。本機症狀不自動授權改部署或長期架構；是否降低本機依賴仍須原成果與裁定支持。 |
| CodeGraph 找到跨模組直寫，與有效介面衝突 | 圖只證明現況可達，原約束不自動失效；停相關寫入，依 §5 分清實作缺陷、方案問題與方向／契約變更。其他歷史直寫不自動成為合法例外。 |
| 跨目錄的小型樣式／文件修正，架構圖較舊 | 若已有足夠契約且未碰舊圖內容，不全面查圖、不更新整本、不建立索引；真正受影響原文才依原規劃窄核與更新。 |

上述是處置示例，不是實際採用成效；不能據此宣稱已降低偏軸或維護成本。

## 7 · 採用與停用

先確認使用的套件規則樹包含 `modules/architecture/`。原授權涵蓋專案設定寫入時，在既有 `.wf/config.json` 的 `modules` 清單加入 `architecture`，保留其他鍵與模組，例如：

```json
{"modules": ["tdd", "codegraph", "architecture"]}
```

其他模組並非前置；只採架構模組可用 `{"modules": ["architecture"]}`。
依既有載入契約，`brief` 只在需求、規劃、執行、審核各注入該階段短文；結案沒有本模組文件。共用說明由內容角色按需讀，不自動展開，也不新增設定鍵或角色路由。
啟用只提供指引，不建立專案架構、不啟用 CodeGraph、不授予索引／安裝或其他寫入權。

停用時只移除清單中的 `architecture`，保留其他名稱；若它是唯一模組，移除 `modules` 鍵或設為 `null`，不要留下不合法的空清單 `[]`。降版到沒有本模組的版本前也先移除名稱。
停用只停止階段注入，不刪專案文件，也不撤銷原已有效的架構決策或專案規範；如需撤銷仍依原來源與裁定處理。
