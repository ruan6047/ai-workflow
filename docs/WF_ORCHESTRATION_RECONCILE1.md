## 0. 這份設計要解什麼

卡面痛點：開卡、scope 變更、交付、審查、CI、merge、部署、release 分散在規則、人工記憶與不完整 CLI；GitHub 限流或中斷後沒有可恢復狀態，導致卡片／看板／main 長期漂移。

「沒有可恢復狀態」不是抽象風險。2026-08-11 一天之內，本 repo 自身發生四件可查證的漂移（§8），其中三件的成因完全相同：**規則寫在文件裡，而唯一寫入通道不執行它**。這與同期 #15／#17 處理的「契約寫著 fail-closed、消費者實際 fail-open」是同一個病，只是換了層面——那邊是消費端沒實作，這邊是編排端沒實作。

因此本設計的判準不是「規則是否完備」，而是**每一條規則是否有機械執行者**。設計文件裡任何一條「應該要…」若找不到對應的動詞、守衛或對帳項，它就不算設計完成。

## 2. 狀態機：轉換表

**狀態集合＝現有凍結枚舉**（`FIELD_SPECS` 的 `交付狀態` 13 值 ＋ 獨立的 `部署狀態` 7 值）。本設計**不新增任何狀態值**（Q6）。

PR 是否開啟、CI 是否綠、merge 是否進 main——這些**不設欄位**，而是轉換的**守衛條件** [guard]，由動詞與 reconcile 即時向平台讀取。

### 2.0 R3-001：前一版是同一個病的第三個實例

R3 依 checkpoint 改版後的規格，只搜尋「用不完備的自訂分類覆蓋已完備的權威分類」，找到了：

> §2 先宣稱狀態集合等於 `FIELD_SPECS` 的 13 值，**隨即用一張只涵蓋 6 個狀態的自訂表取代既有狀態機**。💡需求、⏳待執行、🔨執行中、📦已合併、⏸阻塞、🚨已升級、🛑已停止 七個狀態沒有任何前置／後置或恢復規則。尤其 `merge` 被寫成 `✅通過 → ✅通過`，與 canonical `AI_WORKFLOW.md:18` 的「…`✅通過 → 📦已合併 → 🏁完成`」直接相衝，也與 `worktree-lifecycle.md` 第 11 行「`📦已合併` **仍算現役、仍佔資源交集檢查**」相衝。

**指控成立。** 而且「宣稱 ＝ 凍結枚舉，實際只用 6 個」比前兩次更露骨——**我把完備性寫在句子裡，然後在下一段違反它**。

自查時另外發現同節還有**第四個實例**（見 §2.3）：`release` 的 cleanup 序列同樣是 `worktree-lifecycle.md` 既有七步清單的殘缺自訂版。R3 沒點到，但病灶相同，一併修。

> **兩個必須誠實指出、但本設計不擅自解決的既有不一致**（發現於本輪對照，屬 canonical／實作層，非本卡射程）：
>
> 1. **`🔨執行中` 與 `🚧進行中` 並存**：`FIELD_SPECS` 兩值都有，canonical `:18` 的序列寫 `🔨執行中`，而 `wfcli assign`／`handoff` 實際寫入 `🚧進行中`。**兩者語意重疊，實務上只有後者被寫入**。本設計把兩者並列為同一格，**不合併、不刪除**——那是枚舉變更，須另走紅線。
> 2. **`📦已合併` 的資源語意有兩種說法**：`worktree-lifecycle.md` 第 11 行說它「仍算現役、仍佔資源交集檢查」，同檔第 3 小項卻說「merge 後該卡 `file:` 資源即釋放（改宣告，或直接走完本清單）」；而 `assign_cmd.py` 的 `TERMINAL_STATUSES` 只有 `{🏁完成, 🛑已停止}`，實作上 `📦已合併` **確實仍佔資源**。上表採**實作現況**（佔用），並把「merge 後想提前釋放 `file:` 資源須顯式 `amend` 資源宣告」寫成明示動作，而非自動效果。

**橫跨所有動詞的兩條**：

- **首寫自描述**（§4.2）：凡多次遠端寫入者，第一次寫入須能推導其餘。現況逐動詞稽核見 §4.3——`handoff`／`assign` 尚未合格。
- **`assign` 的跨 repo 拒絕不是死路**：被拒者的合法路徑是去工作所在的 repo 開卡，兩張卡互相連結（§7.1）。

### 2.2 `escalation-checkpoint` 是 review 的守衛，不是可選記錄

`review-escalation.md` §4 要求第三個及其後每個可計數 attempt 出現前先建立 `escalation-checkpoint`；同檔第 173 行進一步規定，**同根因跨三個 attempt，或前一 attempt 的 accepted blocking finding 未在下一輪列 `resolved`／`withdrawn` 時，`checkpoint_decision` 只能是 `escalate`**，不得信任手填的 `continue`。

本設計把它列為 `review` 的機械守衛（§2.1）：第三個可計數 attempt 起，無 checkpoint 事件即拒絕轉錄。

> **本卡自己是實例。** R3 即第三個可計數 attempt，門檻於 2026-08-11 觸發：`marker-scope-narrows-away-safety-signal` 與 `universal-pr-ci-conflicts-with-canonical-classification` 連兩輪未閉環。checkpoint 已建立、需求方裁定 `continue` 並改變 R3 查核規格（改為只搜尋同族第三個實例——**R3-001 即該規格的產物**）。
>
> 但 checkpoint **只能以留言記錄**：`wfcli` 沒有對應 writer（`open`／`assign`／`amend`／`deploy-declare`／`deploy-state`／`handoff`／`review`／`doctor`／`snapshot`）。`counts_toward_escalation` 是人工計算而非 adapter 導出，依 `review-escalation.md` 第 172 行的精神**在寫入通道落地前不具權威**。這正是 §8.5 的形態在本卡上重演，歸 [#9](https://github.com/ruan6047/ai-workflow/issues/9) 與 §9-I。

### 2.3 `release` 的後置動作＝既有結案清單（Q6；R3 自查補正）

**`✅通過`／`📦已合併` 都不是終態**，資源在 `assign_cmd.py` 的 `TERMINAL_STATUSES`（`{🏁完成, 🛑已停止}`）之前不釋放，因此 `release` 轉換**必須**內含收尾。

**前一版在這裡犯了與 R3-001 相同的錯**：我自訂了一條六步序列（`cd 出 worktree → 移除 worktree → 刪本地分支 → 刪遠端分支 → 關閉 Issue → 寫 🏁完成`），而 `worktree-lifecycle.md` 第 11 行**已有一份完備的七步結案清單**。對照後我的版本漏了五項：**merge 後在 main 上重跑 lint／測試並 push**、**資源宣告釋放**、**卡檔封存**、**Ledger 投影重建**、**對帳三件套**。

**修正：不再自訂序列，直接引用既有清單。**

> `release` 的守衛 ＝ `worktree-lifecycle.md` 第 11 行七步清單全數完成。本設計**不重述其內容**（重述就是製造第二份會漂移的複本），只做兩件事：
>
> 1. 把「清單是否走完」從**人的記憶**改為 `release` 動詞的**守衛條件**；
> 2. 讓 `reconcile` 能逐項機械檢查其中可檢查的項目（worktree 是否移除、雙端分支是否刪除、Issue 是否關閉、merge commit 是否為 main 祖先、Ledger 投影是否與狀態面一致）。

清單中「lint／測試在 main 上重跑」與「卡檔封存」屬需要執行的動作而非可讀狀態，`release` 要求其**證據**（測試輸出、封存 commit）而非自行執行。

cleanup 不是「善後」而是轉換的一部分——把它當成獨立的、可選的收尾，就會出現 §8.2 的事故。

## 3. 事件契約

### 3.1 `state_version`：排序權威（Q3）

每個 lifecycle 事件必帶 per-card 嚴格遞增整數。**這是計數不是時刻**，與時間語意契約（cpbl#123）正交。

- **取號**：讀該卡現有最大序號 +1。GitHub 無原子遞增，故取號是 read-modify-write。
- **撞號**（同卡同序號兩筆）→ 並行寫入的證據 → **fail-closed**：該卡降純偵測，人工裁定。
- **缺號**（序列有洞）→ 有事件遺失或未落地 → 同樣降級。
- **舊事件無序號** → legacy epoch，以 `contract-baseline` 劃界（Q11），不追溯。

#### 撞號的機械預防（R1-003 後半）

初版只寫「單 writer 紀律」。查核者指出：**任兩個 resume 或人工作業即可撞號並讓該卡永久降級**——紀律不是機制，而降級是不可逆的懲罰，代價與防護不對稱。

canonical `AI_WORKFLOW.md:148` 已給出可用的一層：「本機可採**原子目錄鎖**；跨主機必須使用具併發控制的服務或 workflow。Markdown、聊天訊息與『請勿同時操作』皆不構成鎖。」

因此分兩層，**不宣稱超出各層真實能力**：

| 併發來源 | 機制 | 保證強度 |
|---|---|---|
| 同機多個 `wfcli` 程序（含 resume 與人工並行——**實測中最常見的來源**） | 以 `(owner, project, card_id)` 為鍵的**本機原子目錄鎖**，包住「讀最大序號 → 寫首寫」整段 | **可預防**。canonical 明文允許，且是鎖不是狀態面 |
| 跨主機 | 無可用的併發控制服務 | **不可預防**。取號後、寫入前**重讀比對**縮窗，撞號 fail-closed |

> **誠實界線**：跨主機撞號仍只能偵測。這與 `wfcli amend` 的「重讀比對縮窗、不宣稱 CAS」是同一誠實等級。但**同機這一層已從紀律升格為機制**，而那正是查核者舉的兩個實例（resume、人工作業）所在的層。

### 3.2 受管轄判準的收窄（Q8，經 R1-002 修正）— 契約修訂案

**現行**（`handoff-contract.md` §3.1.4）：留言**任何位置**出現事件 marker 前綴即受管轄。

#### 3.2.1 R1-002 打穿了原本的純首行判準

初版收窄為「唯有首行構成事件宣告，其餘位置一律散文」，論據是「採信路徑只看首行，中段 marker 不可能被誤採信」。**這個論據答錯了問題。**查核者的反例：

> 同一 `source_sha` 已 APPROVE 後，受授權 writer 因模板前置摘要或 serializer 回歸，把 REQUEST_CHANGES 的事件 marker 寫在**第 2 行**，且在 Project／Log 寫入前 crash。現行規則會 halt 整卡，阻止沿用舊 APPROVE 通過 merge guard；純首行規則會把它降為散文，於是**唯一可機械辨識的降級訊號被忽略**，舊 APPROVE 繼續有效。

失效方向不是「誤採信一則假裁決」，而是**漏檢一則真裁決**。原論據只覆蓋前者。**「實測零次」不構成零損失的證明**——那只說明這條路徑還沒被走到。

#### 3.2.2 R2-001：第一次修訂留了一個洞

改成「獨佔一行且構成**完整** marker 形狀」之後，查核者指出仍有一類沒有歸屬：

> 獨佔一行、帶 marker 前綴、但**缺閉合符號或欄位被截斷**。它既不是「完整形狀」，也不是「非獨佔整行的位置」。

於是同一個失效還在：受授權 writer 把 REQUEST_CHANGES 的 marker 寫在第 2 行、serializer 又產出截斷內容，該留言落進定義的縫裡 → 不停機 → 舊 APPROVE 續用。

**根因是判準不是全函數**：我用「完整形狀」當分類器，而「不完整」沒有被定義到任何一格。**分類器只要有縫，最危險的東西就會待在縫裡**——這是同一個 root cause 第二次以不同外觀出現。

#### 3.2.3 修訂為全函數的三分類

先用一個**只看行首、必定可判定**的謂詞把每一行二分，再在其中細分。三類互斥且窮盡：

> **宣告行** [declaration line]：該行去除前後空白後，**以 `<!--` 起始，且緊接（容許空白）事件 marker 前綴**。
>
> | 分類 | 定義 | 處置 |
> |---|---|---|
> | **完整** | 宣告行，且完全符合單行 marker 文法（閉合符號存在、三個必填欄位齊備且格式合規） | **位於首行** → 事件，可採信<br>**不在首行** → **停機** |
> | **畸形** | 宣告行，但不符完整文法——**未閉合、截斷、缺欄、欄位格式錯誤、版本未知，任何位置** | **一律停機** |
> | **行內引用** | 非宣告行，但文字中出現前綴 | 散文，不受管轄、不觸發停機 |

判準因此是**「行首是否起始一個事件宣告」**——一個可直接判定的謂詞，不需要先確認該行是否完整。完整與否只用來決定「可採信」或「停機」，**不再用來決定是否受管轄**。縫因此消失：每一行落在且僅落在一格。

仍然不進「列舉 Markdown 語境」的賽局——不需要知道該行在引言、清單還是表格裡。

**代價（明文）**：留言若在行首寫出 `<!--` ＋前綴（例如程式碼區塊內從行首開始貼一個範例 marker），即使意在說明也會停機。這是**刻意選擇的保守側**——寫作紀律可規避，漏檢真裁決不可補救。

#### 3.2.4 這個切法能同時成立，是實測出來的

以 §3.2.3 的謂詞對 #15／#17 全部含前綴的留言逐則重新分類：

| 留言 | 宣告行 | 行內引用 | 判定 |
|---|---|---|---|
| #15 `5238836386` | **無** | 第 27、31 行 | 不受管轄 → 解凍 |
| #15 `5239013086` | **無** | 第 40 行 | 不受管轄 → 解凍 |
| #15 `5239153770` | **無** | 第 43 行 | 不受管轄 → 解凍 |
| #15 `5239231631` | 第 1 行（完整） | — | 事件，可採信 |
| #17 `5243803972` | 第 1 行（完整） | — | 事件，可採信 |

把三張卡凍住的那三則派審留言，前綴**全部只出現在行中，沒有任何一行以宣告形式起始**；真正的事件留言則是首行完整。**故三分類同時做到：#15／#17 解凍、R1-002 的完整 marker 反例停機、R2-001 的截斷 marker 反例也停機。**

**仍會停機的**：首行畸形、非首行的完整 marker、**任何位置的畸形宣告行**、同 attempt 跨留言重複（落差 8a 不受影響）。

**失去的**：僅「行中出現前綴」這一類——它在任何規則下都不可能被採信，也不可能承載裁決。

#### 3.2.5 連帶後果與待補證據

- #15／#17 自動解凍，無需為歷史留言補 clearance。
- `templates/dispatch-package.md` 於 2026-08-11 加入的留言引用紀律**改寫而非移除**：規則從「不得出現前綴」放寬為「**不得讓任何一行以 `<!--` ＋前綴起始**」。行中引用自此安全。
- **回歸探針為驗收條件，非選配**（R1-002／R2-001 disposition）：實作卡 §9-C 必須附**真實 timeline** 的回歸測試，最少覆蓋——
  1. 上表五則真實留言的三分類結果；
  2. 「**完整** marker 在第 2 行 ＋ Project／Log 未寫」的半寫入次序；
  3. 「**未閉合／截斷** marker 在第 2 行 ＋ Project／Log 未寫」的半寫入次序（R2-001 新增）；
  4. 行首起始但版本未知的宣告行。

  合成 fixture 不足以驗收——這正是 #17 漏抓的原因。

### 3.3 `wf-review-clearance:v1`：停機解除的留言平面表示法（Q8）

落差 7 的根因是 `review-escalation.md` §5 定義了 clearance 的**欄位**，卻未定義它在 GitHub 留言平面**長什麼樣**，消費者無從辨識，亦無 writer。

比照事件的既有模式（外層用四個反引號，否則內層 fence 會提前終止外層——這正是本輪轉錄踩到的同一類問題）：

````
<!-- wf-review-clearance:v1 card_id=<CARD_ID> quarantined_comment_id=<id> state_version=<n> -->
## 停機解除：<clearance_decision>

（人類可讀敘述）

```yaml
（§5 全欄位：quarantined_comment_url、quarantined_comment_author、
  quarantined_body_sha256、quarantine_reason、clearance_decision、
  superseding_attempt_id／repaired_body_sha256、incident_record_url、
  cleared_by、clearance_rationale）
```
````

- **首行 marker 承載識別**；clearance marker 適用**與事件 marker 相同的 §3.2.3 三分類**（宣告行完整且在首行→可採信；宣告行畸形或不在首行→停機；行內引用→散文）。**fenced 區塊承載全欄位**（同 Q9 模式）。
- writer：新 `wfcli` 動詞（實作卡 §9-C）。clearance 事件同樣帶 `state_version`。
- 消費端判定沿用 `review-escalation.md` §5 既有規則（雙欄相符、hash 變動即重新停機、`forged-rejected` 不自動解除等），本設計**不改其語意**，只補表示法。

### 3.4 裁決留言的結構化區塊（Q9，落差 8b）

`render_verdict_comment` 於散文後附 fenced YAML，承載 #15 Q9 已定的**語意比對基準**：

```yaml
state_version: <n>
review_result: APPROVE | REQUEST_CHANGES
core_pain_resolved: yes | no
delivery_status: ✅通過 | ↩退回
findings:
  - finding_id: <id>
    accepted: <bool>
    status: open | resolved | withdrawn
```

刻意**排除**寫入時間與 reviewer 自由文字（它們每次執行都不同，納入即無法比對）。

- **marker 三鍵不動**，不觸發 v1→v2 全域 cutover。
- 消費端：同 attempt 兩則事件的區塊語意相等 → 冪等重送，放行；不等或**任一缺區塊** → 維持停機。
- 歷史留言無區塊 → 天然落保守側，無需 cutover 儀式。
- **區塊為機器權威、散文為人類渲染**，兩者同源產出；不一致即為竄改證據 → 停機。

## 4. 自描述首寫與恢復（Q1／Q4，經 R1-001 改寫）

### 4.1 為什麼原本的 WAL 不能留

初版採預寫意圖日誌：動手前把意圖 append 到本機 `~/.config/wfcli/outbox.jsonl`，crash 後靠它得知要補哪一步。查核者指出這違反 canonical，複驗屬實：

- `AI_WORKFLOW.md:143`：「專案若採本機 inbox/outbox，runtime 必須 `.gitignore`，**只可引用 remote handoff event**。」尚未存在於 GitHub 的意圖，不是任何 remote event 的引用。
- `AI_WORKFLOW.md:165`：「狀態面不可用時（平台中斷）狀態操作暫停：**不得改用聊天、本機檔案或記憶暫代**。已派工作可續作，狀態轉換等恢復後補寫。」WAL 正是拿本機檔案暫代狀態轉換。

這不是措辭問題。WAL 一旦成為 resume 的唯一輸入，它就是決定狀態面該長什麼樣的權威，而它只存在於一台機器上——**卡面驗證條文第三項（不得與 GitHub single-source-of-truth 衝突）當場不成立**。

### 4.2 正解：把恢復資訊放進第一次遠端寫入

原設計問錯了問題。它問「crash 之後怎麼知道做到哪」，於是需要一份本機紀錄。**該問的是「為什麼第一次遠端寫入沒有把意圖說完」。**

> **自描述首寫原則**：任何多次遠端寫入的動詞，其**第一次寫入必須自描述**——單獨讀它就足以推導出後續每一步該寫什麼。

於是 crash 只有兩種情形，兩種都不需要本機狀態：

| crash 位置 | 遠端痕跡 | 恢復方式 |
|---|---|---|
| **第一次寫入之前** | 零 | 什麼都沒發生。重跑安全，**沒有東西要 resume** |
| **第一次寫入之後的任何位置** | 首寫已在 GitHub，且自描述 | 任何人、任何機器讀 GitHub 即可推導缺哪幾步並補齊 |

本機零狀態。canonical 兩條都不再踩到：沒有本機檔案暫代狀態，平台中斷時操作自然暫停（首寫失敗＝零痕跡＝重跑）。

**這比 WAL 強，不只是合規**：WAL 的恢復資訊隨機器一起死，且明文放棄跨機（原 §4.3）。自描述首寫把恢復資訊放在所有人都看得到的地方——**機器毀了照樣救得回來，別台機器也能接手**。原本自承的單機限制隨之消失。

### 4.3 逐動詞稽核（依 `cli/src/wf_cli/commands/` 現行實作）

| 動詞 | 現行寫入次序 | 首寫自描述？ | 需要的改動 |
|---|---|---|---|
| `review` | **Issue 留言** → 交付狀態欄 → body Log | **接近合格**。碼內註解已寫明「先留言、後翻狀態」的理由，方向正確 | 留言需帶 §3.4 結構化區塊，使後兩步**可推導**而非僅「可辨識」 |
| `amend` | **body Log** → 級別欄（僅需要時） | **合格**。Log 行已記 `原值 → 新值`，欄位寫入可由它推導 | 補 `state_version` |
| `handoff` | owner 欄 → 交付狀態欄 → 最後交接欄 → iteration 欄 → body Log | **不合格**。首寫是單一欄位，讀它推不出其餘三欄與 Log | 改為首寫一則自描述留言（或先寫 body Log），其餘為導出 |
| `assign` | owner 欄 → 分支worktree 欄 → 交付狀態欄 → body Log | **不合格**。同上 | 同上 |
| `deploy-state`／`deploy-declare` | 依既有契約 | **未稽核** | 實作卡須先稽核再改 |

> **這張表本身就是 R1-001 的價值**：原設計用一份本機檔案，把「三個動詞的首寫不自描述」這個結構缺陷蓋住了。拿掉 WAL 之後缺陷立刻顯形，而且是**可逐條修完**的。

### 4.4 恢復與 reconcile 的關係

恢復不再是獨立機制，而是 §5 reconcile 的一個輸入來源：**讀 GitHub → 發現首寫存在但導出物缺漏 → 依首寫補齊**。這讓 §5.2 白名單第 1、2 條（原本描述 WAL 未解除項）併為單一條件：**首寫存在、其導出物缺漏、且該動詞已通過 §4.3 自描述稽核**。

> **這裡刻意不使用「重放結果唯一」**：那個詞在 §5.4 被判定為未定義，不能一邊退回第 3 條、一邊在第 1 條偷用它。第 1 條的前提是**單一自描述物件的推導**，不是整條 timeline 的收斂——推導的輸入就是那一則首寫，輸出由 renderer 的既有映射決定，兩者都是既存且可測的東西。

`half_written`（#20）因此從「事後偵測到一個需要人判斷的狀態」升級為「**帶有明確修復輸入的狀態**」——缺什麼由首寫說了算。

### 4.5 殘餘限制（明文）

- **首寫不自描述的動詞在改完之前無法恢復**：`handoff`、`assign` 現況如此，`deploy-*` 未稽核。這些動詞的半寫入仍只能偵測、交人。**這是已知缺口，不宣稱解決**（實作卡 §9-B）。
- **惰性恢復的延遲**：狀態面停在不一致直到下次有人跑 `wfcli`。這是 Q1 無常駐程序的已知代價，未變。
- **首寫本身失敗且非原子**：若 GitHub 在留言 API 內部半成功（罕見），首寫的自描述性不保證。此情形落 §5.3 純偵測。

## 5. reconcile：分層權限（Q2）

### 5.1 預設純偵測

列出所有分歧＋每項的精確修復指令。零寫入。

### 5.2 `--apply` 白名單（**窮舉，白名單外一律 fail-closed**）

初版四條中，第 1、2 條建立在 WAL 上（隨 R1-001 作廢），第 3 條建立在「重放結果唯一」而**該詞從未定義**（R1-003）。修訂後：

| # | 分歧形態 | 自動修復動作 | 前提 | 狀態 |
|---|---|---|---|---|
| 1 | 首寫存在於 GitHub，其導出物（欄位／Log）缺漏 | 依 §4.2 自首寫推導並補齊 | 首寫自描述（§4.3 稽核通過的動詞）；序號未撞 | **啟用** |
| 2 | 卡已 merge（`📦已合併`，或未走 `merge` 動詞而停在 `✅通過` 的歷史卡），但 worktree／分支殘留、Issue 未關 | 逐項檢查並補齊 §2.3 引用的既有結案清單中**可機械檢查**的項目 | merge commit 確為 main 祖先；需執行的項目（main 重跑測試、卡檔封存）僅回報缺漏，不代為執行 | **啟用** |
| 3 | ~~完整重放後 `交付狀態` 落後事件流終態 → 補寫欄位~~ | — | — | **退回純偵測**，見 §5.4 |

第 1 條的安全性不再靠「重放結果唯一」這種散文前提，而靠一個**可查證的物件**：首寫。它要嘛在 GitHub 上、要嘛不在；它要嘛自描述、要嘛不是（§4.3 逐動詞列出）。

**每筆修復 append Log 記原值**（沿用 `wfcli amend` 已確立的紀律）。

### 5.3 白名單外——一律純偵測，交人

停機（`marker_quarantined`）、裁決衝突、順序歧義、撞號／缺號、混世代卡、首寫不自描述之動詞的半寫入（§4.5）、任何需要語意判斷者。

> **硬前提（Q2）**：白名單修復必須基於**完整 timeline 重放**，不是單點比對。「欄位 ≠ 最後一則裁決結論」不必然是半寫入——可能是裁決後又合法 handoff 回去了。單看最後一則裁決去「修」欄位，會把合法的後續狀態倒退回去。**排序不可靠的卡（撞號／缺號／legacy epoch）一律降回純偵測。**

### 5.4 為什麼第 3 條退回純偵測（R1-003）

查核者的指控成立且精確：第 3 條把自動改寫欄位的安全性**全押在「完整重放結果唯一」**，而本設計未定義任何一項使該判定可機械執行的東西——

- 所有動詞的**可解析事件表示**（版本化 envelope）
- **total reducer**（每個事件型別對狀態的作用，含 legacy、`review-correction`、clearance、半寫入）
- **未知 type／缺欄策略**
- **「唯一」的判定演算法**本身

而事件與結果散在 Issue 留言、body Log、Project 欄位三面，混入上述型別後，「結果是否唯一」**正是需要 reducer 才能回答的問題**——用散文前提替代它，等於把最危險的一步留白。

**處置**：第 3 條在下列全部就緒前不進白名單，此為**驗收條件而非建議**：

1. 版本化 event envelope，涵蓋所有 lifecycle 動詞。
2. total reducer：對每個 `(狀態, 事件)` 有定義的輸出，含未知 type 與缺欄的明文行為（方向為 fail-closed）。
3. 明確的完整輸入集合（三面各取什麼、如何合併）。
4. 每一種 non-unique／不可解析結果的枚舉與對應處置。
5. 測試矩陣，覆蓋上述每一格。

在此之前，「欄位落後事件流」只列為分歧並印出建議指令，**不自動寫**。歸實作卡 §9-G。

## 6. PR＋CI 的適用範圍（Q7，經 R1-006 限縮）

### 6.1 為什麼原本的「全統一」不成立

canonical 明文保留了直推路徑，而初版 §6 靜默覆蓋它：

- `AI_WORKFLOW.md:14`：B1 記錄文件「直接 commit；免審，不部署」。
- `:24`／`:25`：T0 記錄、T1 編修「直接 commit」。
- `:54`：「**required status checks 不是預設要求**：對 §0 允許的 B1／T0–T1 直推 main 工作流，它會鎖死既有路徑。」

**更關鍵的是 §8.4 的證據被我誤讀了。** 那四張直接 merge 的卡（#15／#17／#19／#20）是 T2／T3——canonical `:54` 尾句本來就寫著「T2 以上程式碼仍必須走分支與獨立查核」。所以 §8.4 證明的是「**既有分類沒有機械執行者**」，不是「分類切錯了」。用它去推翻分類，是拿執行缺口當政策依據。

真正該補的是執行者，不是改政策。

### 6.2 修訂後的範圍

初版限縮仍然過寬（R2-002）：它把**全部**權威治理文件納入強制 PR＋CI，而 canonical B2 那一列寫得比我引用的更細——

> `AI_WORKFLOW.md:15`：「B2 權威文件｜spec、規則、API、checklist｜**小改可直接 commit**；需獨立事實查核／校讀，不部署；**canonical 規則本體與指定 T4 文件除外**。」

canonical **自己已經劃好了界**：B2 的預設是小改直推＋獨立事實查核，例外是「canonical 規則本體」與「指定 T4 文件」。我等於把 canonical 的例外擴張成通則，還宣稱不需要修 canonical——**那是把覆蓋說成釐清**。

**適用 PR＋CI（三者取聯集）**：

1. **T2 以上的程式碼變更**（canonical 既有要求，本設計只是補上機械守衛）。
2. **canonical 規則本體**：`AI_WORKFLOW.md` 及其直接承載規則的檔案。
3. **指定 T4 文件**，以及**需求方明示升級**的個案。

**維持直推**：B1 記錄文件、T0 記錄、T1 編修，**以及 B2 權威文件的小改**（`templates/` 下範本、`MODEL_ROUTING.md` 等的非結構性修訂）——一如 canonical。

> B2 小改直推**不等於免審**：canonical 同一列要求「獨立事實查核／校讀」，且 `:20` 明文「B2 的獨立事實查核不得被 T1 省略」。這條約束不變，本設計不碰它。**PR＋CI 與獨立查核是兩件事，初版把它們綁在一起是錯的。**
>
> #15 之所以該走 PR，不是因為「它是治理文件」，而是因為它改的是**契約本體**（`handoff-contract.md` §3.1 的權威條文），落在第 2 類。這個區分初版沒做出來。

**因此本設計不需要 canonical 修訂**——修訂後的範圍與 canonical B2 的例外條款逐字對齊，沒有擴張。

### 6.3 其餘規則（未變）

- **merge 方式**：保留 merge commit（no-squash）。**squash 會改寫 SHA，`source_sha` 綁定的整套契約會斷**。
- **執行者**：需求方授權 → 執行者 `gh pr merge`。授權與 merge 都落在平台可查的物件上。
- **sign-off 守衛**：`db_scope ∈ {schema, data-migration}` 或 needs-deploy 卡，**CI 綠是必要非充分**，merge 前另需需求方 sign-off 事件。
- **ai-workflow 需補最小 CI**（現無 `.github/workflows/`）：至少跑 `cd cli && uv run pytest`。實作卡 §9-F。

### 6.4 狀態機須補的 PR 事件契約（R1-006 後半）

查核者指出：初版只喊政策，沒把 PR 生命週期接進狀態機。補上——

| 環節 | executor | 事件／守衛 |
|---|---|---|
| PR 建立 | 執行者 | `handoff --next-stage review` 的守衛：適用範圍內的卡，PR 必須存在且 head ＝ `source_sha` |
| CI 觀測 | 平台導出，不設欄位（Q6） | `merge` 動詞即時讀 checks 結論 |
| CI 失敗恢復 | 執行者 | 推新 commit → 重新 `handoff`，`source_sha` 隨之更新；**不得在原 attempt 上默默改** |
| sign-off | 需求方 | 平台可查物件（PR review approve 或 Issue 留言事件），`merge` 守衛檢查其存在且對應同一 `source_sha` |

**逐 repo 落地**（ruleset／CI workflow 的實際套用）列為實作卡 §9-F 的驗收項，不在本設計宣稱已完成。

## 7. worktree 對帳（Q10）

- **repo 歸屬純導出**：卡的 repo ← Issue URL；worktree 的 repo ← git `commondir`。兩者不合 → 跨 repo 建立，機械可偵測。
- **`assign` 寫入時預防**：`--worktree` 的 commondir repo ≠ 卡 Issue repo → **拒絕派工**。只偵測不預防的下場見 §8.3。

### 7.1 跨 repo 工作的合法路徑（R1-005）

查核者指出初版自相矛盾：§7 一律拒絕跨 repo 註冊，§8.7 卻聲稱 registry 可機械表達跨 repo 對應。**被拒絕的東西不可能同時被登記。** 二者擇一，這裡選「一律拒絕」，並補上被拒絕之後該走哪條路：

> **工作落在哪個 repo，卡就必須開在哪個 repo。** 跨 repo 的需求以**連結卡**表達：來源 repo 的卡（如 cpbl#116）在 spec 基線宣告實作卡的 Issue URL，實作 repo 的卡（ai-workflow 內）反向連回。兩張卡各自在自己的 repo 內走完整生命週期，各自持有自己的資源宣告與 worktree。

如此 `assign` 的拒絕不再是死路：它把人推向「去正確的 repo 開卡」，而不是「想辦法繞過檢查」。連結關係落在卡面欄位上，兩端都看得到。

**明文不宣稱的**：這**不阻止**任何人直接在別的 repo 開分支手動做事——那是人的操作選擇，`assign` 只管註冊制 worktree。已知殘餘風險。

### 7.2 資源宣告的互斥語意（R4-001）

#### 既有權威已經把話說對了，是實作與本設計沒跟上

- canonical `AI_WORKFLOW.md:145`：「**共享可寫資源必須宣告並互斥**：`file:<path>`、`port:<n>`、`container:<name>`…」
- `control-plane-contract.md:49`：「派工前資源交集比對：〈命令；**比對本卡寫入集 × 現役卡寫入集**，撞則排隊〉」

**「寫入集相交」是既有契約的用語。** 而 `cli/src/wf_cli/resources.py` 的 `find_conflicts` 實作為「完全相同字串才算撞（不做路徑前綴模糊比對，避免誤判）」——**字串相等是寫入集相交的一個不完備的代理**。前一版把它寫成 `assign` 的安全守衛「資源宣告無交集」，等於用這個代理冒充保證。

線上有現成反例：**#16 宣告 `file:templates/`、#22 宣告 `file:templates/review-escalation.md`，寫入集實際重疊，現行檢查卻判無衝突、兩張可同時派工。**

#### 需求方裁定：階層路徑包含比對

> 兩個 `file:` 資源相交，當且僅當**其正規化路徑相等，或其一為另一之祖先目錄**。判定以**路徑邊界**為準：`file:templates/` 與 `file:templates/a.md` 相交；`file:templates/` 與 `file:templates2/a.md` **不相交**。路徑先正規化（去除 `./`、重複斜線、結尾斜線統一標示目錄）。

選此案而非「禁止目錄宣告、一律精確檔案」的理由：**只有目錄宣告能表達「我會在這裡新增檔案」**，而那是真實需求（本卡自己就是）。逐檔宣告會迫使每新增一個檔案就 `amend` 一次，摩擦大到一定程度就會造成少宣告——**保護會被繞過而不是被遵守**。

實作註解所稱「避免誤判」，指的是樸素子字串比對（`templates` 命中 `templates2`）；**加上路徑邊界判定即無此問題**，該顧慮不構成反對本案的理由。

#### 過渡期：混用一律 fail-closed

在階層比對實作並測試完成前，**目錄宣告與其子檔案混用的兩張卡一律視為衝突、不得 `assign`**。

> **立即後果（誠實記錄）**：本卡 §7.2 生效後，#22（`file:templates/review-escalation.md`）在 #16（`file:templates/`）進入終態或 `amend` 其資源宣告前**不得派工**。
>
> 這正好推翻我在 #22 開卡時的斷言、以及我隨後的「更正」——**兩次我都答錯了**。第一次是未查證即斷言互斥；第二次查了實作，得到「不衝突」的正確描述，卻把它當成正確的**規範**，還把它歸為「非本卡射程」。**實作現況不等於契約應然**，而本卡的職責正是讓兩者對齊。

#### 歸屬

契約語意定義在本卡；`find_conflicts` 的階層比對實作與測試（含 `templates/` vs `templates2/` 的邊界案例、以及 #16／#22 的真實反例）歸實作卡 **§9-L**。在該卡落地前，過渡期的 fail-closed 由 PM 人工執行。
- **primary worktree** ← `git worktree list` 首項，分類為 primary，**永不列孤兒**（修正既有誤報）。
- **合法跨 repo 沙箱**：使用 detached worktree（沿用既有 `detached_sandbox` 分類），不走註冊制。
- **registry `github` 模式**：實作讀 Project 的 `分支worktree` 欄位。ai-workflow 自 08-04 cutover 後 `TASKS.md` 僅為封存投影，doctor 目前實際上無 registry 可讀。

卡面痛點是「部署生命週期無法透過唯一寫入通道轉換」。查證現況，漂移比卡面描述更嚴重：

| 事實 | 狀態 |
|---|---|
| 卡：cpbl-analytics#116 | `OPEN`，執行欄仍為「待指派」 |
| 實作：`deploy-state`／`deploy-declare` | **早已在 ai-workflow `main`**（`cli.py` 已註冊兩個子指令） |
| 分支：`origin/codex/WFCLI-DEPLOY-STATE1` | **仍殘留於 ai-workflow**；查核者複驗其 tip **已是 `main` 祖先**，故為**已合併未剪除**，非未合併程式碼 |

**碼交付了、分支沒剪、卡從未推進。** 根因是卡與工作分屬兩個 repo：卡在 cpbl，實作在 ai-workflow，而兩端都沒有機制看見另一端——cpbl 的看板不知道碼已上線，ai-workflow 的 `doctor` 不知道那條分支對應哪張卡（其 registry 只讀本 repo 的 `TASKS.md`）。

**本設計的恢復路徑**（R1-005 後改寫——初版聲稱三項「合力恢復」，但其中一項與 §7 相斥）：

2. **§7 registry `github` 模式 ＋ 孤兒分支偵測**：對**已經存在**的此類殘留，doctor 能偵測到「本 repo 有一條分支，無任何本 repo 的卡認領它」，並因其 tip 已是 main 祖先而判定剪除安全。
3. **§2.3 `release` 引用既有結案清單**：未來的卡，分支剪除是轉換守衛的一部分，孤兒不會無聲累積。

> **邊界誠實聲明（R1-005 後收緊）**：對**存量**的此類漂移，機械能力止於「偵測到一條無人認領但可安全剪除的分支」。**它無法把那條分支歸屬到 cpbl#116**——跨 repo 的歸屬關係從未被登記過，而本設計選擇了「一律拒絕跨 repo 註冊」，因此也不會事後補建這種登記。**歸屬需要人。** 初版說三項「合力，缺一不可」地完成恢復，是把預防、偵測與清理混為一談，該說法撤回。
>
> 同樣不宣稱解決：直接在別的 repo 開分支手動做事仍在射程外（§7.1 末）。

## 10. cutover 程序（Q11，經 R1-004 修訂）

### 10.1 初版的矛盾

查核者指出 §10.4 與 §10.5 沒有區分兩種不同的保護，於是同時宣稱了互相衝突的兩件事：

- 「含 legacy epoch 的卡**永久純偵測**」
- 「在途卡不中斷，**後續動作自動受新制**」

而且量測結果讓這不是邊角問題：**線上 6/6 張 OPEN 卡全部早於 cutover**（#9、#10、#11 於 08-06～08-07 建立，#13 於 08-08，#16／#21 於 08-10；已複驗）。若混世代卡永久降級，cutover 當下就有 100% 的活卡拿不到本卡要交付的自動恢復能力，且空窗期＝這批卡的存活期，未知且無上限。

### 10.2 兩種保護必須分開講

| 保護 | 需要什麼 | 對混世代卡 |
|---|---|---|
| **寫入守衛**（`assign` 拒跨 repo、`review` 要 checkpoint、`merge` 要 CI 綠、`release` 要 cleanup、首寫自描述） | 只看**當下這一次寫入**，不需要歷史 | **cutover 當下立即全面生效**，不分新舊卡 |
| **reconcile 自動修復**（§5.2 白名單） | 需要**可重放的歷史** | 需要一個可信的起點 |

初版把兩者混講。分開之後矛盾消失：在途卡的**後續動作**確實立刻受新制（那是寫入守衛），而**自動修復**才需要處理歷史。

### 10.3 legacy prefix 的錨定（取代「永久降級」）

不回填、不追溯，但也不放棄——用一個**遠端 one-shot 事件**把歷史切掉：

> 對每張混世代卡，追加一則 `epoch-anchor` 事件，內容為**當下由三面導出的狀態快照**（交付狀態、部署狀態、owner、iteration、resource claims），並指派 `state_version = 1`。

- 這是 **append，不是改寫**——完全符合 append-only。
- 錨點**之前**的事件視為不透明前綴，reducer 不解析它們，只把錨點快照當作初始狀態。
- 錨點**之後**的事件序號連續、可重放，該卡因此**取得完整的自動修復能力**。
- 錨定由需求方或 PM 明示執行（它宣稱「當下狀態就是這樣」，是一個需要人負責的斷言），**不自動批次跑**。

### 10.4 程序

1. 契約修訂 PR 先行（§3.2／§3.3）——收窄落地後 #15／#17 自動解凍。
2. 實作卡 A（序號）落地。
3. 以既有 one-shot `contract-baseline` 事件劃線。**線後所有寫入**適用新制的**寫入守衛**，不分新舊卡，立即生效。
4. 對 6 張在途卡逐張執行 §10.3 的 `epoch-anchor`。**這是有界的工作量（6 張），不是無限期空窗。**
5. 未錨定的卡：自動修復降純偵測，寫入守衛照常生效。

### 10.5 殘餘

未錨定卡在錨定前拿不到自動修復。**但空窗現在是可量測、可收斂的**（分母 6，動作明確），而非初版那種「等它們自然結案」的無限期。若某張卡因故無法錨定（例如三面狀態本身就不一致，快照無法誠實產生），該卡留在純偵測——**這正是它應該待的地方**。
