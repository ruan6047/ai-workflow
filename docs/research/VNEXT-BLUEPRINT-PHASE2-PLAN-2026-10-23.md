# 藍圖第二階段完整規劃

## 方案及第一階段增量

選定「既有方向本體承載成果分期、各卡核定規劃承載具體前置、既有共同協調安排共享操作」。需要分期或跨卡取捨的專案，能回答：哪個使用者成果應先得到、這次交付到哪裡、哪個操作實際缺什麼、何時可並行、變動影響誰，以及成果證據支持到什麼程度。提供完整的建立、使用、改動及回看路徑，但不建立通用排程平台。

現行依據是上述 main 固定版本：`core/boundaries.md` §3 已完成方向內容、四種權威、改動生命週期及各階段成果回看；`PM-coordination.md` §2 已明訂第二階段輸入與責任；`stages/規劃.md` §1／§2 已限制本卡輸入並要求判定相依／並行。其他直接依據為 `core/flow.md` §3–§8、`core/github.md` §1／§4／§6、五階段文件與採用指南 §4。第一階段舊提案僅供背景，未生效文字不當現行規則。

本階段新增的是可操作的成果里程碑、四類依賴／約束、前置解除證據、並行與順序理由，以及這些內容的變更銜接。沿用第一階段權威分離、需求承接、有限影響處置及本卡／上位成果區分，不重建或重驗第一階段。

| 可信選項 | 評估與不採用理由 |
|---|---|
| 既有本體＋各卡具體前置＋既有協調，選定 | 可重建成果與順序決定；狀態、資源及技術判斷仍在原權威，不增加工具或角色 |
| 全部只放個別任務規劃 | 小型任務可如此做；跨卡成果沒有共同判準時，容易各卡完成卻無人知道產品成果是否成立，不足以作完整第二階段方案 |
| 統一藍圖檔、必填依賴表或全案甘特圖 | 容易把估時與順序變成期限、誤設整張卡前置，並要求無分期需求的專案多維護一份文件 |
| GitHub 新欄位、依賴圖引擎及自動狀態同步 | 目前需要的是內容判斷與可核實證據；自動推斷相依、調度及雙份進度會擴大 CLI 與資料權威 |
| 固定里程碑批准及每卡結案後重確認全案 | 會增加全局關卡與上位驗收負擔；原階段活動和成果證據足以承載回看 |

## 使用者、決策與唯一權威

| 使用者／責任 | 需作的決定 | 唯一來源與界線 |
|---|---|---|
| 需求方 | 分期成果、必需／可延後內容、價值與優先取捨、縮減／取消／替代 | 有效方向本體及需求方裁定；不能由技術人員或排序表自行改產品成果 |
| 受派規劃／執行內容角色 | 技術或資料前提是否真實、解除證據是否足夠、隔離／並行及影響範圍 | 消費該前置的本卡核定規劃；前置契約／版本／結果的事實取自原交付物、原研究或既有證據來源，不另抄一份方案 |
| 本卡 PM | 將本卡需承接的部分帶入需求／派工，忠實登記裁定及原成果結論 | 本卡需求與階段卡；不作技術或產品成效判斷，不寫其他卡 |
| 共同協調 | 已裁定優先下的跨卡衝突、共享操作次序及有界變動協調 | 既有裁定／核定規劃中的安排與來源索引；不新增第五種交界事件，不常駐管理進度 |
| 本卡正式審核者 | 本卡聲稱與解除／成果證據是否符合本卡契約 | 本卡核定需求、規劃及受審成果；不替全案重新驗收，不替別卡免審 |

方向本體保存里程碑成果及已裁定的分期／優先理由，必要時連到候選任務或成果證據；消費者本卡規劃保存自身操作的具體前置；共同協調安排只保存操作次序及其原來源。生產者的實際交付版本與證據仍在原成果居所。任務狀態、期限及目前資源占用只在既有 GitHub Project 欄位，技術規範仍由 `.wf/` 宣告決定。上述權威互不代寫。

本次不需新增框架持久文件或採用專案的必備文件。方向分期沿既有本體的適用段落；前置和步驟沿本卡原規劃階段完成留言；事實證據沿原成果位置；變動沿原裁定／阻塞／結案留言。單次任務沒有分期需求，直接使用本卡規劃即可。只有未來實際出現獨立長期讀者／決策用途，且既有居所不足，才依原主要成果邊界提出新文件，不在本方案預建。

## 成果里程碑如何表達與判定

里程碑 [Milestone] 是使用者可辨識的階段成果，不是框架階段、任務群狀態、卡片計數或統一通關條件。需要時用自由文字或小表格表達：連到哪個已確認目標／成功條件、使用者在什麼範圍得到什麼結果、本期必需與可延後事項，以及足以支持聲稱的最小成果證據。沒有用到的內容不為格式硬湊。

需求方決定成果與取捨；受派內容角色依本次成果判斷怎樣的直接證據足夠，將本卡真正承接部分列進原需求／規劃。需跨卡合成的成果證據，應在已有合適任務的需求／規劃中指定誰產生、原位置及回看時機，不能留給不具名的未來 PM。若形成另一主要成果，沿原入口另行分流，不能附帶擴張某張小卡。

審核者只判本卡承接的證據與聲稱；跨卡產品結果需真人判斷時，依既有規劃列人工檢視及角色，不另加里程碑審核。需求方對成果／風險的決定仍沿原需求、規劃、審核或裁定活動。PM 忠實登記已有結論，不能自行判定成效。

里程碑回看於相關任務原階段交付、既有結案回報，或影響該成果的既有取捨事件進行，不要求每卡每階段同步整本。證據可在現有本體保留有來源的產品結果敘述，或本體只連原結論；不複製每卡進度。內容需要正式更新時由受派內容角色處理，結案 PM 不代改本體。

「已達成」「部分成立」「未驗證」「被替代」均為附範圍與證據的內容敘述，不新增流程狀態或固定值域。全部卡片完成、程式合併、部署成功各自只是證據的一部分；若尚無跨卡使用者成果證據，里程碑仍應說未證實。上位未證實不能倒過來阻擋範圍已完成的小卡結案，也不自動生成追蹤任務。

## 四類依賴／約束與解除方式

針對確實影響本次工作的關係，說清「哪個消費操作需要哪個具體成果／輸入／契約／版本、原因、目前證據與限制、最小解除條件」。由原材料可識別即可，不強制編號、欄位、表格或新依賴檔。

| 類別 | 真正限制與判定責任 | 什麼足以解除；什麼不是解除 |
|---|---|---|
| 技術必需 | 某操作不能在缺少指定契約／成果時正確完成；內容角色以研究及方案判定 | 指定版本的輸入已可取得，與消費者核定前提相符且有直接證據；不是生產者整卡關閉、口頭說快完成或卡片連線本身 |
| 資料／外部前提 | 指定資料版本、權限、外部可用性或使用者操作等實質條件 | 原來源可核實、範圍與使用模式符合原授權、具體資料／結果已就緒；不能以虛構樣本或舊資料冒充實際條件 |
| 業務希望先後 | 需求方基於價值／成本／時效選擇先交付某成果 | 有效取捨所涵蓋的優先安排；它不證明後項技術不可先開發，改排序也不給新增範圍或資源授權 |
| 共享資源互斥 | 指定共享寫入／整合操作會衝突，由內容角色判定實際交集，既有共同協調安排操作順序 | 操作前確認當前基準、占用、必要租用／授權及隔離證據；先前排程或空的時間欄不是鎖，也不能阻擋隔離實作 |

每項關係如實說明是已知事實、推論或尚未釐清及其來源；這是內容敘述，不增加流程狀態。只有證據支持的實質風險才安排有界釐清，問題及終點依原研究規則，不為假想極小概率增加研究或產品工作。

**不等整卡的解鎖**：前置若只是可讀契約或固定資料樣本，取得該具體交付並核對後，可依本卡原核定範圍展開隔離開發，無須等待生產者其他工作結束。尚未通過其正式程序的候選成果必須標明身份、固定識別及限制；使用者能否承受變動由本卡原規劃決定。這不代表前置卡已驗收，也不免除兩卡後續正式審核、整合、部署或資料授權。正式／不可逆操作仍須核對該操作真正需要的已核定版本與證據。只用候選物完成的演練，不宣稱正式契約或產品已成立。

**相連卡輸入限制**：現行 `core/github.md` §1 自動帶入相連卡的需求／非目標及登記規劃，僅供判斷歸屬，不能把其方案作為本卡規劃輸入。第二階段不改此契約。需要消費的接口、資料與解除條件先由本卡需求／核定規劃明確承接，技術事實由本卡內容角色窄讀或核對原交付／研究證據；在本卡原交付或規劃中留來源。引用只取本次必需部分，工具不自動展開、不遞迴整本藍圖或相連卡的連結，亦不因引用而接手他卡工作。

**循環、假依賴及失效**：先檢查循環是否只是把業務排序、共享窗口或整張卡關閉誤寫成技術前置；內容角色以具體操作與證據拆解。若確有契約互相依賴，可提出固定接口、可替換樣本、先做一條垂直路徑或調整分工的方案，仍須符合本卡核定邊界，不能自行改公開契約或別卡範圍。查不清、證據矛盾或版本失效時，只停消費該前提的操作並回報；涉及方向／風險取捨交需求方，涉及方案缺陷沿原退回。沒有自動圖遍歷、循環檢查器或全案重新排程。

## 執行順序的決策規則

先尋找能讓使用者得到可核對價值的一條端到端路徑 [End-to-end Path]，再增加覆蓋或自動化。不能一律先完成全部底層再碰畫面；同時不能為了快有畫面省略該成果必需的資料真實性、安全或契約。實際前提以證據判定，非固定架構教條。

內容角色先指出必須串行的具體操作及可隔離並行的部分；需求方裁定價值優先與成本／風險取捨；共同協調依既定安排處理共享操作次序，不作技術判定或每步批准。已核定且無交集的工作直接續行。順序表不是技術互斥、實作授權或新的截止日；預估與真正期限不同，期限仍由原欄位及裁定維護，不在藍圖複製。

已核定範圍內、依賴不被違反且不改風險／驗收的局部步驟調整，沿現行執行規則說明即可，不每次重確認。新成本、新動作或方向取捨才交原裁定處理。整合基準、外部窗口、資源占用與權限等即時條件，在實際操作前查核；不前置成數日隔離實作的等待。

## 建立、使用及改動生命週期

| 時機／使用者 | 使用的適用片段與動作 | 邊界及留下的結果 |
|---|---|---|
| 建立或採用本體，需求方及受派內容角色 | 沿有效目標與既有里程碑／任務關係；只補本次成果分期與實質前提 | 有效既定決定直接引用；候選不能自動生效，沿既有需求／規劃／裁定確定，無新的藍圖確認 |
| 共同入口收新案 | 相關里程碑、成果邊界、已裁定優先及已知關係 | 查重、保留來源與本次貢獻後分流，不在入口設計全部技術依賴或卡內規劃 |
| 每卡 PM 需求與派工 | 本卡承接哪個成果、不能承接什麼、影響本次的取捨與來源 | 留原需求／裁定；相連卡仍只判歸屬，不擴張驗收或增加整本注入 |
| 每卡規劃 | 已承接成果及原研究／交付事實 | 形成自身具體前置、解除證據、隔離／串行理由、證據責任及回看點，放原核定規劃 |
| 執行 | 自身核定計畫及本次操作前提 | 核對消費版本／資料／當前共享條件；交付證據與限制，失效只停相關操作，不擅自替上游補做 |
| 審核 | 本卡契約、核定規劃及當時已存在證據 | 核對解鎖與產品聲稱是否有據，不替上位驗收、不使候選前置免審，不等待未來自然事件 |
| 結案或已有跨卡成果回看事件 | 實際交付、原合成證據及內容／審核結論 | 同一回報區分本卡完成、里程碑成立範圍及未證實部分，PM 不代判產品成效；本體需改由內容角色在允許階段處理 |

任何角色可對里程碑／前置／排序提出帶來源、原因、受影響結果及建議處置的候選。純客觀交付事實由原成果證據支持；可在核定邊界內處理的步驟調整不增加批准。實質改變成果分期、業務優先、範圍或已接受風險，沿原需求方裁定；技術假設／方案失效依原規劃／執行規則處理，不能把所有變動一概升成新需求或一概當小調整。

受派內容角色同步修改有效本體及直接引用：方向／里程碑本體記產品取捨，消費者計畫記本次前置變更，原交付證據保留實際版本。保留舊來源並標明取代／取消範圍；取消一個里程碑不等於原目標達成。既有共同協調僅在本次衝突／取捨事件協調已知受影響卡，各卡 PM 引用同一裁定處置，不巡查全歷史、不要求每個進度變化同步所有人。

| 變動 | 本體與相關卡如何處理 | 未受影響部分 |
|---|---|---|
| 部分交付／外部延誤 | 說明哪些結果已有證據、哪個操作缺何條件；前置未滿只停消費操作；改承諾或接受新風險才交原裁定 | 隔離開發、其他里程碑及既有有效證據續用 |
| 縮減或取消 | 需求方裁定保留／排除的成果與剩餘問題；主要成果變動的卡依原流程退回需求，不做者走原停止；不把刪驗收當完成 | 不因一項取消批次退回所有卡 |
| 替代／合併 | 指明接手的具體成果、接口／資料來源、原證據可沿用範圍及殘留風險；新前置由內容角色核對 | 卡號換名不是等價性或達成證據，未變契約不重跑原完整流程 |
| 插單／排序調整 | 需求方決定價值取捨，共同協調重排有交集的操作；若只在既定安排內且無交集直接續行 | 不因高優先插單撤銷其他卡授權、不自動賦予部署或資料權限 |
| 真依賴失效／互相矛盾 | 內容角色界定失效的版本、消費者及證據；必要回到本卡規劃，若成果方向需變才回需求；按原規則處理審核失效範圍 | 不把已失效結果當仍可沿用，也不重審無關成果 |

正在執行卡不因新藍圖文字自動改範圍；先停相關操作、保存已做成果及來源，再依原裁定或合法退回處理。已占用資源由原占用卡按既有釋放條件確認程序停止與必要恢復；未知就明示未知、只停下一次相關寫入。不能因排程取消而直接宣稱鎖已釋放、刪除資源，亦不空等舊 PM 回覆；接手仍依原可核實停止證據及安全交接規則。

## 完整短例：虛構「社區活動網站」的資料更新

以下全是合成情境與假設決定，只示範框架使用，不指涉真實專案或授權任何操作。文中的代稱只方便閱讀，不是要求採用的 ID。假設需求方已確認：居民能查到可核對版本與更新時點的活動資訊；資料失效時不誤認為最新；先有可用查閱，再自動化更新。本期不做推播或個人帳號。

| 成果里程碑 | 必需與可延後邊界 | 證據、產生者、判定及原居所 |
|---|---|---|
| 可核對的查閱 | 在核定預覽環境查閱一份已確認快照，顯示來源、資料時點與版本；可延後自動抓取、所有分類覆蓋 | 畫面讀到與指定快照一致內容的端到端紀錄，頁面任務執行者在其既有交付產生；本卡審核核對，真人檢視依原安排；證據連原快照與交付成果，不用合併代替 |
| 新資料能被使用者讀到 | 核定來源的一次真實新版更新能經網站顯示，資料時點及版本一致；可延後排程頻率及更多來源 | 更新任務執行者在本卡已核定的端到端交付保存來源版本→發布版本→頁面讀到版本的同一條證據；需資料及環境授權；審核只核對此已承接成果 |
| 更新失敗仍不誤導 | 更新失敗時保留最後成功資料且標示待更新，後續成功後標示與版本一致；可延後異常推播 | 更新／呈現任務各提供其契約證據，跨卡組合由更新任務原規劃明示的執行者產生並存在原交付；依既有審核及人工安排核對，不另設里程碑批准 |

少量候選任務只列成果及原來源，沒有狀態／進度／資源占用副本：

| 候選任務 | 主要成果與里程碑關係 | 自身需承接的前置／證據 |
|---|---|---|
| 快照讀取 | 供應可核對來源／時點／版本的資料讀取契約及一份確認快照 | 原來源與資料使用範圍；交付固定契約與快照識別，支援第一條可用路徑 |
| 查閱呈現 | 頁面呈現指定快照及版本時點，服務第一里程碑 | 隔離開發可用固定候選契約及明示樣本；核定預覽聲稱需相符的已核定快照與讀取版本 |
| 更新發布 | 新版更新成為網站可讀資料並保留最後成功版本，承接第二／第三里程碑中明示的更新成果 | 更新所需輸入契約、實際來源資料、資料授權與正式發布操作條件；本卡原規劃安排跨卡端到端證據，不是後補全案驗收 |
| 失效呈現 | 網站顯示失敗／待更新與恢復後狀況，承接第三里程碑的呈現部分 | 固定結果描述的契約及範例；可隔離開發，不負責替上游取得資料或實作發布 |

四類關係的可用記法：

| 關係及理由 | 具體前置、現有認知、最小解除 | 不可誤推 |
|---|---|---|
| 技術：查閱／失效呈現消費快照與結果契約 | 已知候選契約 `snapshot-read v1@樣本交付甲`；消費者核對指定字段語意與範例後即可在隔離環境開發；正式整合前另核對已核定契約版本 | 不等快照讀取卡其他文件收尾或關卡，也不假稱候選已正式審核 |
| 資料／外部：真實更新需新版來源 | 已知目前只有確認舊快照，尚未取得有權使用的新版；取得指定來源新版及符合用途的資料授權才可作該次真實更新 | 舊快照／合成新資料能做演練，但不能證明第二里程碑成立 |
| 業務：先讓居民可查，再擴自動更新 | 假設需求方因立即查閱價值已裁定優先交付查閱；取捨來源留原裁定 | 失效呈現技術獨立時可並行，不能把此優先序畫成必須等查閱卡關閉的依賴 |
| 共享：發布與既有例行維護同用預覽環境的單一更新目標 | 已知只有發布操作有交集；真正窗口、基準及占用在操作前由原協調與內容角色核對，遵守原租用及授權 | 本機／隔離實作不等待共享窗口；安排一個時段不代表已取得寫入權限或互斥鎖 |

**初始順序與並行**：先提供最小固定快照契約，同時開始頁面骨架與更新流程的隔離設計；契約及樣本可讀後，查閱與失效呈現分開消費所需部分並行，更新發布可用明示的合成輸入做已核定開發。儘早在核定預覽環境交出「確認快照→查閱」端到端成果，再將真實新版接入更新鏈。更新發布的共享操作與例行維護串行；各自隔離實作並行。沒有「全部底層完工才做 UI」，也沒有為了先出畫面宣稱真實更新已驗證。

**局部失效與縮減**：外部新版延誤只阻真實新版發布及其里程碑聲稱，查閱與失效呈現可依核定契約續行。若需求方後來決定本期取消自動更新、以「匯入已核准檔案」替代，內容角色保留原來源目標及自動化尚未完成的限制，更新分期與直接引用；原更新發布卡依實際裁定停止或改方向退回需求，候選匯入任務沿原入口承接，不由舊卡直接擴做。可復用資料讀取與查閱成果不重做；失效呈現若接口未變則續用，若結果語意變更只重估相關消費操作。停止共享程序、釋放占用及確認新資料權限，仍各依原證據／授權，不能由替代裁定自動推定。

**結案與里程碑回看**：若原更新發布卡仍承接真實端到端成果，缺該證據就是本卡未完成，不能合法結案。另一種合法情況是前述縮減裁定已停止原更新發布卡，將新匯入任務明確縮為「可讀取核准檔案並輸出候選快照」，且需求方已決定本期暫不安排組合驗證。此時全部保留小卡可各按自身契約關閉，但各卡只完成隔離／元件證據，第二里程碑仍不能寫已達成；應說原自動更新成果已取消／被替代，新的手動產品成果尚未證實。這是明確的暫緩決定，不是假設未具名的未來角色會補證據。第一里程碑若已有相符的預覽查閱證據可說其核定範圍成立；第三里程碑若只有元件層失效標示紀錄，就只說部分證據成立。不能以全關卡、停止、替代、合併或部署紀錄湊成全案成功，也不倒加組合驗收要求已完成小卡重開。
