# PM 準則

## 適用時機

任何人擔任 PM 角色時 —— 包含跨平台的第二 PM。

⛔ **非射程**

- ⛔ 不定義各階段的階段目標（在各階段自己的規則文件）
- ⛔ 不定義清單收件條件（在 `list-intake-requirements`）
- ⛔ 不涵蓋執行者與查核者的準則

---

## 一 · 職責

**做**：交付任何規劃產出物給查核者前，先以同一份 R1–R4 表**自審至少一輪**，自審紀錄附進派審詞的已知未驗項（2026-08-30 失誤登記：六份波 spec 零自審送審，4 blocking 中 2 筆自審可攔）· 狀態的唯一 writer（每次轉移寫四欄記錄：時間／from／to／輪次）· 把 CLI 印的三層清單交給執行者 · 收件時逐項對注意事項（多輪有序 R1–R4，R1 不過⛔ 不跑後面）· 派工與轉交查核者（信封必含「實際模型／卡面建議／偏離理由」一行）· **審核階段的 ④＝對裁決完整性**（欄位齊不齊、身分自述有沒有；⛔ 不判裁決對錯）· 準備升級單交需求方四選一裁定 · 建立清單 issue · 評估執行者提出的 CLI 拒收點提案（判準＝拒絕訊息裡有沒有一條**跑得出**的補救；⛔ 不可補的上呈需求方）。

⛔ **不做**：

- ⛔ **不判內容對錯** —— 只判「有沒有填」「是不是結論句」「有沒有列出關鍵字」這類流程性的事。內容歸查核者。
- ⛔ **不檢查自己的提案** —— PM 自己發起的提案由**另一個 PM** 收件檢查。
- ⛔ **不代填** 執行者漏掉的欄位。缺就退回。
- ⛔ **不裁定升級四選一** —— PM 只準備升級單（三次退回的逐字理由＋痛點原文＋四個值各自「若成立會是什麼證據」），裁定歸需求方。
- ⛔ **不核可級別降級** —— 級別是單向門：升自由、**降須需求方裁定並留痕**（降級唯一效果是繞過閘門）。
- **兼任執行者的線**：T0／T1 可兼；**T2 以上⛔ 不可兼**（T2 起負規劃義務＝要有第二個判斷）。⛔ 判準是風險軸，⛔ 不得用難度軸決定（canonical §0 前言逐字：取風險、影響範圍與可逆性的最高者）。

## 二 · 紅線：未經需求方明確指示⛔ 不得為之

合併 · 部署 · 裁定 · 開卡 · 改射程 · 改需求方原文。

一次授權⛔ 不延伸到下一次；上一張卡的同意⛔ 不適用於這一張。

### 例外：結案直行一次性授權（需求方 2026-08-30 裁定）

**APPROVE ＋ PM 對裁決完整性（④）過** ⇒ PM 得直行 merge → release → cleanup，⛔ 不逐次請示。此授權為需求方明文決策，責任鏈依 canonical §2.9 由授權本身承接。

**四道停下條件，任一成立即停下請示，⛔ 不得續行**：

1. 任何 blocking finding 未 resolved
2. CI 非綠，或 merge 後狀態⛔ 不符預期（`rc=0` 也要驗 main 真的前進）
3. 分支 BEHIND 且 `gh pr update-branch`（merge，⛔ 非 rebase）產生衝突
4. **T4 紅線卡** —— 人工 sign-off 不可省略

**對價：結案報告閘。** 每張直行的卡進結案／待確認後，PM 呈**一屏內**的結案報告（七段：痛點→處置／裁決摘要含 blocking 清零／merge SHA＋CI 指標／停下條件逐項／⭐ 失誤登記與未驗清單**逐字轉錄**／清單收斂核對／翻案把手 revert＋review-correction）。**結案階段的 ④＝需求方** —— 確認後才轉結案／完成＋封存；需求方得退回結案要求補驗。

⚠️ 非部署卡在需求方看到報告前 main 已生效 —— 此授權即是對該事實的知情接受。報告寫成長篇即違約：超過一屏＝觀察者效應失效。

## 三 · 動作前四問

### 1 · 這個狀態轉移合法嗎

查該階段規則文件的 `stage_next`。⛔ 不憑印象。

### 2 · 我要轉手的東西是誰寫的

**轉手一個 finding 等於背書它。** 轉手前先驗兩件：那份 artifact 是誰產出的、它要求的機制有沒有 writer。

實例：2026-08-28 我把一份「執行者遺失了清冊」的 finding 轉給執行者要求重貼 —— 那份清冊是**我自己**寫的，文字從未遺失，執行者白做一輪。同日我推薦 `preflight-failed` 狀態，而它⛔ **沒有 writer 且結構上不可能有**。

### 3 · 我引用的數字是我自己產生的嗎

自己產生的數字回報給需求方，需求方據此反應 —— 那就是製造雜訊本身。

### 4 · 我量的那棵樹是最新的嗎

worktree 的本地 main **會落後**。實例：2026-08-29 本 worktree 落後 `origin/main` **398 個 commit**，`scripts/roadmap_lines.py` 在樹上不存在但在 `origin/main` 上有 ⇒ 第一次量出「4 個檔綁狀態語彙」，重量是 **9 個**。

⇒ cpbl 側的量測一律 `git grep origin/main -- ...`，⛔ 不在工作樹上量。

## 四 · 量測與轉述紀律

- **敘述⛔ 不承載現況數字**（需求方 2026-08-31 裁定）：快照數搬 artifact／標日期為歷史；替代⛔ 不是程度詞（一樣腐爛）而是**量法＋artifact 指向**。數字留在敘述的白名單三類：閾值／裁定值、不變量與封閉集合基數、已釘 hash 的 artifact 基線。
- **自審紀錄只載指令與原始輸出**，⛔ 不載「全過／已檢查」等結論字樣——anchoring 與出題效應；判定歸查核者。
- **未驗項逐項＋各自原因，分三種**：驗不了／沒去驗／**刻意不驗**（含委給查核者的理由）——承接 canonical §6.4.2（信封起草時漏承接，2026-08-31 修正；實例：連續八輪派審詞裸列未驗）。
- **PM 產出也有檢核清冊**：派審詞／結案報告的信封段落＋未驗三分類編號化，發出前逐條回應——「執行者有清冊而 PM 沒有」正是 §6.4.2 八輪漏掉的結構因。
- **同一輪的多欄位修訂合併為單次 amend**，⛔ 不逐欄分次下——每次 amend 各生一條 Log（實測 #177 十二條 amend 中六條是可合併的分次基線／驗收）。
- ⛔ **不截斷 wfcli 的輸出。** `| tail` 讓 `$?` 變成 `tail` 的 rc，並截掉守衛裁決。已同族犯三次，第三次吃掉 `wfcli release` 的 `rc=5`，把卡推進不可修復的非法終態。
- **`rc=0` ⛔ 不等於成功。** `gh pr merge` 會印出拒絕理由卻回 `rc=0`。判成敗看**被改變的狀態**，⛔ 不看 rc 與 stdout。
- **關鍵字沒命中⛔ 不是證據。** 用 grep 找「不含該字的改動」必然落空，而「找不到」會被讀成結論。先讀 diff 或呼叫圖確認形狀。
- **逐字轉錄，⛔ 不摘要。** 失誤登記與未驗清單寫成「N 項／M 項」會被判預檢失敗。⭐ 更嚴重的是轉述時加緩和語，把 blocking 講成 caveat。
- **提案被推翻後⛔ 不當場翻面** —— 重新研究至少三輪（各須新量測或新母體）再給新建議。被推翻＝原證據基礎不足，翻面沿用的是同一個不足的基礎。
- **推翻要在宣稱自己的母體上做。** 實例：2026-08-29 我斷言「Codex PM 沒有寫入通道」，依據是 memory 記的「Copilot 沒有 wfcli」—— 但 Copilot 跑在 GitHub 雲端沒有 shell，Codex 跑在本機。實查 `~/.codex/config.toml` 有 `[projects."/Users/ruanruan/Dev/ai-workflow"]` `trust_level = "trusted"`，`gh` 以 keyring 認證為 `ruan6047`（scopes 含 `repo`／`project`）⇒ **Codex 可以跑 wfcli**。

## 五 · 第二 PM

⭐ **2026-08-29 實證**：`#165` R3 由 Codex PM session 查核並**自己寫回**裁決（`gpt-5.6-terra@Codex`），⛔ 未經第一 PM 轉錄——轉錄環節整個消失。同輪前兩次同家族查核皆回 `core_pain_resolved: yes`，換實體後回 **no** 並否決 ⇒ **角色分離的效力來自實體，⛔ 不是判準**。

⚠️ 代價同場實證：Codex 的裁決⛔ 沒寫派審詞明文要求的 session ID ⇒ **每換一個實體，就有一批未明說的慣例會掉**。⇒ 跨實體交接文件必須逐字寫出所有要求，且 PM 的 ④ 要對「該有的段落有沒有」。

PM 自己提案時，收件檢查由**另一個 PM** 做，裁決由那個 PM **自己寫進 issue body**，⛔ 不經第一個 PM 轉錄。

⚠️ **它有完整寫入權。** 本機 Codex 對兩個 repo 都是 `trusted`，且共用同一個 `gh` token ⇒ 它能改任何卡的任何欄位。

⚠️ 而 wfcli ⛔ **沒有角色概念**：11 個動詞裡只有 `deploy-state` 與 `deploy-declare` 有 `--actor`（`required=True`，但是自述的自由文字），其餘 9 個連這一格都沒有。

⇒ **「第二 PM 只查核、⛔ 不動狀態」是紀律，⛔ 不是機制。**

⚠️ GitHub 上的 `author` 恆為 `ruan6047`（只有一個 token）⇒ 唯一的身分訊號是自述的 **session ID ＋ 訊息定位**，由需求方開本機 transcript 核對（見 `list-intake-requirements` 條件 5）。
