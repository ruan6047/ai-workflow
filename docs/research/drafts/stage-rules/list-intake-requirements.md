# 待審清單收件條件

## 適用時機

有人發現一個問題、或想要一個功能，要把它交給 PM 進待審清單時。提案者可以是人，也可以是執行其他卡時撞到問題的 AI。

⛔ **非射程**

- ⛔ 不判斷這件事該不該做 —— 那是開卡之後、需求階段 R1 的事
- ⛔ 不判斷內容對不對 —— PM 只看下列四項有沒有填
- ⛔ 不涵蓋「清單項 → 卡」的升級（那走 `open --from-issue`）
- ⛔ 不涵蓋清單的清理 —— 清單當墓地是可接受的，它不佔看板欄位、不進盤點分母、不參與任何檢查

---

## 條件 1 · 出處可指

**寫什麼**：一個連結，或逐字引文加來源。

AI 在執行其他卡時撞到的，寫「在哪張卡的哪一步撞到」。例：`執行 aiwf#165 A3 掃描時，在 snapshot_population.py:5 撞到`。

**PM 怎麼判**：有沒有指得到的地方。⛔ 不判那個地方對不對。

**退**：只有「我發現……」而沒有任何可指之處。

---

## 條件 2 · 是觀察不是結論

**寫什麼**：可觀測的現象。形狀是「X 指向 Y，但 Y 不存在」「A 每天跑，B 從沒讀過它」。

⛔ **不寫**：「應該改成 Z」「因為 W 所以要……」「這是設計缺陷」。

**PM 怎麼判**：句子裡有沒有解法，或有沒有未經量測的因果推論。有 ⇒ 退。

**為什麼**：寫成結論會把解法空間先關掉。2026-08-26 有兩張卡的身分欄寫成「怎麼判」與尚未量測的結構假設，兩張都因此鎖死射程、只能停卡重開。

---

## 條件 3 · 查重留痕

**寫什麼**：**逐字列出搜過的關鍵字**，加上命中的 issue 編號。

```bash
gh issue list --repo ruan6047/<repo> --state all --search "<關鍵字>"
```

清單項與既有卡都是 issue，⇒ 一次搜尋同時涵蓋兩者，⛔ 不需要兩套查法。

⛔ **不寫**：「已確認沒有重複」。

**PM 怎麼判**：有沒有列出關鍵字。⛔ 不判關鍵字選得好不好。

**為什麼**：關鍵字沒命中不等於不存在。「我確認過了」是宣稱，事後⛔ 查不了；「我搜了 A B C，命中 #12 #45」查得了，而且下一個人看得出漏搜了哪個詞。

---

## 條件 4 · 屬哪個 repo

**寫什麼**：`ai-workflow` 或 `cpbl-analytics`。

**判準**：這件事將來會改哪個 repo 的檔案。

**為什麼**：GitHub 搬 issue **會換號碼**，而號碼正是引用它的方式。放錯了就得換一次號。

---

## PM 的動作

四項齊 ⇒ `gh issue create` 到指定 repo，**body 逐字含四項的填答**。

缺任一項 ⇒ 退回提案者補。⛔ PM 不代填。

⚠️ 清單項⛔ **不可配卡ID** —— `open` 的唯一性檢查只看 Project #4 的 items，配了 ID 的清單項不會被找到，同一件事會被開成第二張卡。

⚠️ 清單項⛔ **不可掛成任何卡的 sub-issue** —— Project #4 的 `Auto-add sub-issues to project` workflow 是開著的，掛上去就自動上板，清單與看板的界線當場消失。

---

## 條件 5 · 提案者身分

**寫什麼**：三格，缺一不可。

| 格 | 內容 | 為什麼 |
|---|---|---|
| GitHub 帳號 | 提案者的帳號 | 今天是常數（全部 `ruan6047`），多人協作時才有鑑別力。⚠️ 晚加的代價是舊項全部沒值且⛔ 補不回來 |
| session ID | Claude：`~/.claude/projects/<cwd>/<id>.jsonl` 的 `<id>`；Codex：`~/.codex/archived_sessions/rollout-<時間>-<id>.jsonl` 的 `<id>` | ⭐ 唯一可核對的一格 |
| 該則訊息定位 | Claude：訊息 `uuid`；Codex：該則 `timestamp` | 把核對縮到一則，⛔ 不用讀整份 |

⛔ **不填模型名，⛔ 不填 AI 工具。** transcript 已由 harness 寫入：Claude 每則 assistant 訊息帶 `model`／`version`／`effort`／`isSidechain`；Codex 的 `session_meta` 帶 `originator`／`cli_version`／`git.commit_hash`，`turn_context` 帶 `model`／`effort`。多填一格只是多一個能說謊的地方。

**PM 怎麼判**：三格有沒有填。⛔ 不核對。

**為什麼 session ID 不是自述**：它本身是自述，但它**指向一份本機檔案** —— 而檔案裡的 `model` 是 harness 寫的。⇒ 造假仍可能，但造假**會被抓到**。這是它與「模型名自述」的唯一差別（`doctor.py:502` 逐字：「收據內文的模型／工具名稱仍只是自述，不是身分證明」——那句話講的是**沒有對應物可查**的自述）。

⚠️ 兩份 transcript 都在**本機** ⇒ 只有需求方在這台機器上核對得到，跨家族查核者⛔ 做不到。

⚠️ 這一格的存在是本設計自己造成的：`issue.author` 本來就是 GitHub 記的事實、不可造假，但「PM 是清單唯一 writer」讓所有清單 issue 的 author 都變成 PM。⇒ 多人協作若各自持有 token、自建清單 issue，這一格可以整格拿掉。

## 當提案人是 PM

⛔ **PM 不得檢查自己的提案。** 由**另一個 PM** 做這四項的收件檢查，裁決逐字寫進 issue body，含裁決者身分自述與時間。

**為什麼**：這條閘門的其餘部分⛔ 擋不住 PM 自己。實測 2026-08-28 一天開四張同族卡（`#165`→`#166`→`#167`），⛔ 沒有一張是執行者開的，全部由 PM 開出。「限制誰有寫入權」在此零效果，因為提案者與寫入者是同一個。

⚠️ **這道閘門機械上不成立，效力只來自留痕。** 跨家族查核者⛔ 沒有 wfcli 也⛔ 沒有 gh token；`gh` token 就是需求方本人 ⇒ 任何寫入的 author 都是同一個。第二個 PM 只能給裁決，寫入仍由第一個 PM 執行 ⇒ **它機械上仍是「PM 打的字」**，可信度取決於需求方抽驗轉錄是否逐字。

⛔ 第二個 PM 由誰擔任、原始輸出需求方看不看得到 —— **未定**。

---

## 為什麼四項都要逐字寫進 body

清單項的 issue body 是**唯一可事後查核的地方**。

被 PM 擋下來的提案⛔ 不留痕（它只存在於對話視窗）。⇒ 「這道閘門有沒有在運作」只能從收進去的那些項回推。四項寫得越逐字，回推得越準。
