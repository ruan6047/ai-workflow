## 1. 產品目標

ai-workflow 要讓採用它的專案更快、更省心地交付可靠成果。框架是否成功，以四件事判斷：

1. 需求是否被正確完成。
2. 成果是否容易檢視及重現。
3. 是否避免明顯偏離原始目標。
4. 使用框架是否比需求方直接管理 AI 更省時間與心力。

多階段、多角色與多模型只是在能改善上述結果時使用的手段，不能成為目的。框架不得為單次失誤、推測風險或未出現的使用情境建立大型機制。

## 2. 共通原則

- CLI 提供資訊、載入規則、保存流程狀態與檢查客觀資料；內容判斷由人或負責該內容的 AI 完成。
- 一個概念只有一個權威居所；GitHub 畫面不重複保存同一狀態。
- 一張任務卡只有一個主要成果，並指定一位最終需求方。
- 需求核定後鎖定成果方向。後續階段不得自行改變成果、需求邊界、公開契約、主要驗收或已接受風險。
- 方向改動一律停止目前階段，退回需求階段，由需求方人工裁定。
- 每個正式階段完成時都由需求方確認；一次確認只呈現一個畫面的成果、疑慮與下一步。
- 研究子狀態、正常實作修正、測試重跑及非阻擋觀察不增加獨立確認點。
- 一項驗收提供足以支持結論的最小證據集合；「一份結果」不是「只能有一個測試」。

## 3. 流程

正式流程只有五個階段：需求、規劃、執行、審核、結案。研究是需求或規劃內的選用子狀態，不是獨立階段。

### 3.1 需求

需求階段由需求方與 PM 確認：

- 要解決的問題與主要成果。
- 限制、非目標及已知假設。
- 風險、影響、緊急性與期限。
- 能直接檢查的驗收條件。

需求階段必須執行 Grilling，以逐項提問檢查目標、成果、限制、非目標、假設、風險與驗收是否矛盾。Grilling 只釐清「要什麼」與「為什麼」，不得進行事實研究、技術比較、方案設計、實作規劃或測試設計；需要查證現況時一律進入第 4 節的研究子狀態。

需求／研究只用來確認需求與現況事實是否成立。若研究結果推翻需求假設，回到需求討論，不能把研究結論直接變成實作方案。

### 3.2 規劃

規劃者依已鎖定的需求與研究證據：

- 比較可信的替代方案並選擇技術方向。
- 說明採用及不採用方案的理由。
- 定義影響範圍、執行步驟、分工、風險、回復方式與直接證據。
- 判定相依功能、並行任務與必要回歸範圍。

規劃／研究可以量測、比較及製作可拋棄探針，但不能修改正式成果。若需求本身有誤，必須退回需求階段。

### 3.3 執行

執行者只實作已核定方案。規劃中的檔案與步驟是預估，不是不可變的逐檔清單；執行者可以調整相鄰測試、共用函式或必要實作位置，但不得改變公開契約、主要技術、風險、驗收、資源需求、其他任務責任區域或成果方向。

交付前，執行者必須：

- 完整檢視自己的差異。
- 完成規劃要求的測試與客觀檢查。
- 說明與原規劃不同的局部調整。
- 確認沒有未完成項目或阻擋交付的疑慮。

規劃範圍內、可以理解的實作或測試缺陷允許自行修正。測試重跑不算流程退回，也不計入同根因再次發生。

### 3.4 審核

審核者在乾淨環境中，針對 exact SHA 與預期合併結果，獨立重現或核對直接證據，並檢查需求、規劃、成果、影響範圍、回歸、安全、資料及資源風險。

審核者不得：

- 修改被審成果後，把修改後的結果當成原版本通過。
- 新增驗收標準、偏好的風格要求或推測性機制。
- 代替執行者修正成果或改變任務狀態。

查核環境可以產生建置檔、測試資料與可拋棄探針。環境或權限不足時，只能回報「無法判定」及缺少條件，由 PM 安排補足；不能批准，也不能判定內容失敗。

審核結果只有：批准、退回執行、退回規劃、退回需求。環境不足使用本流程的阻塞狀態，不新增專用狀態。再次審核只檢查先前阻擋項及其相關回歸。

### 3.5 結案

PM 整理結案卡，需求方確認後才可合併。合併後必須驗證 main、CI 與正式成果，再關閉任務並完成必要清理。

若合併後失敗與本次成果有關，原卡不得結案；PM 標記阻塞，修正或回滾一律退回執行階段處理，再重新經過審核與結案。只有確認失敗與本次成果無關，才能另開任務處理，且原卡仍須具備自己的完成證據。

結案階段不得修改成果內容。

## 4. 研究子狀態

每次研究只回答一個明確問題。研究者應：

- 使用多個適當來源；有可信的不同觀點時，呈現共識、分歧、來源品質、時效、偏誤及未知事項。
- 不為了形式上的多元而捏造反方。
- 列出有證據支持的相依項目、可能受影響功能、並行任務衝突與未知事項，避免「修 A 壞 B」。
- 將影響研究限制在已知相依關係及可能影響主要成果的鄰接區域，不做全專案泛查。
- 提供證據與選項，不替規劃者選方案。

PM 派研究任務時，必須標明網路使用為必要、允許或禁止，以及不可送出的資料類型。研究者須簡短列出實際使用的外部工具、資料來源及送出的資料類別，不得傳送憑證、個資、私有原始碼或未授權內容。PM 只檢查聲明是否存在及是否符合派工限制。

## 5. 角色與責任

### 5.1 需求方

- 定義成果並確認各正式階段。
- 裁定方向、成本、風險、公開契約及任務是否停止。
- 核定框架級及使用者級注意事項。
- 可以兼任執行者，但依第 6 節不得擔任該成果的正式審核者；階段確認不等於正式審核。

### 5.2 PM

- 維護專案全貌、優先順序、排程、角色、模型、流程與資源協調。
- 檢查派工資料、證據與交付欄位是否完整，並忠實整理一個畫面的階段確認卡。
- 比對既有紀錄、執行已裁定的流程處置，並在核定後負責合併與結案。
- 可以登記注意事項候選並建議歸屬，但正式內容由執行者修改。

PM 不得研究、規劃、實作或審核專案內容，也不得修改產品程式碼、測試、文件、設定、資料或框架規則。PM 可以維護協調狀態、摘要，並執行唯讀的客觀檢查。

內容角色負責提出問題證據、可能根因與建議退回階段。PM 只檢查資料完整性、辨識已知重複及安排流程；有技術爭議時交由適當的獨立內容角色釐清，仍無法收斂才交需求方裁定。

### 5.3 規劃者

規劃者負責選擇方案、定義影響範圍、步驟、分工、證據與回復方式。規劃者不能修改正式成果，也不能藉規劃擴張已鎖定需求。

### 5.4 執行者

執行者在獨立分支或 worktree 實作核定方案、完成直接檢查並自我審查。發現需求、方案、資源或相依假設失效時，回報現象、證據與影響，不硬把舊卡做完，也不自行擴張方向。

### 5.5 審核者

審核者只作獨立判斷，不修改成果、不接手實作、不新增需求，也不自行改變任務狀態。

## 6. 角色獨立性

- PM 永遠不能兼任內容角色。
- 同一任務的研究者、規劃者及執行者不能成為正式審核者。
- 啟用研究時，研究者與規劃者使用不同工作實體或乾淨工作階段。
- 一般或重要任務的規劃者與執行者可以使用同一平台，但必須是不同乾淨工作階段；高風險任務應分離研究、規劃與執行。
- 正式審核者必須未參與被審內容產出、使用乾淨工作階段，並採用不同模型家族。平台只記錄為呼叫管道，不取代模型家族的獨立性。
- 高風險任務需要兩個獨立審核視角，兩者不得承接彼此尚未完成的結論。

乾淨工作階段是新的 AI 對話或代理工作階段，不承接產出者的私有上下文。程式碼查核使用新的 worktree 或等效的乾淨 checkout，固定到被審 exact SHA。審核者可以讀取正式核定資料，不得沿用產出者未整理的推理。

## 7. 偏移、根因與停止條件

- finding 不能直接變成 patch。內容角色先說明使用者影響、證據、可能根因與唯一責任層，再決定修正位置。
- 優先移除末端例外並修正上游原因；不得為一次失誤在多層新增重複守衛。
- 問題宣告解除並正式交付後，又在審核或後續正式交付中被證實存在，才算同一根因再次發生。此時停止繼續補洞，交需求方裁定。
- 執行中的正常修正、測試失敗與測試重跑不算同根因再次發生。
- iteration 只識別一次執行嘗試，不作升級計數器；退回次數由流程轉移歷史推導，不因達到固定數字而自動增加機制或升級任務。
- 發現者只回報現象、證據與影響。內容角色可以建議退回需求、退回規劃或停止；PM 不做技術裁決。
- 可客觀確認的外部條件暫時不可用時，PM 可以標記阻塞。涉及方向、需求假設、風險接受或是否停止時，一律由需求方人工裁定。
- 缺少證據不代表低風險。若未知事項可能影響安全、資料、正式環境、公開契約或其他主要成果，先安排釐清，再執行相關操作。

注意事項先作卡片級候選。PM 可建議提升到專案層；提升為框架級或使用者級前，必須由需求方確認。正式文件由執行者修改，不因每一則注意事項強制新開任務卡。

## 8. 風險、影響與緊急性

風險／影響分為一般、重要、高風險；緊急性另分一般、限時、緊急。緊急性只影響排程，不降低需求確認、執行自檢、獨立審核或結案證據要求。

任務大小依主要產物切分：程式碼任務聚焦一個行為、文件任務聚焦一個讀者目的、設計任務聚焦一個決策、研究任務聚焦一個問題。行數只作警示，超量時說明合理性，不作硬性拒收。

## 9. 多人協作與共享資源

- 同一時間只有一位當值 PM；每張任務只有一位 owner。
- 狀態寫入前比較任務版本或 `updated_at`。發現內容已變更時拒絕覆寫並重新讀取；第一版不承諾 GitHub 更新具有原子性，也不建立鎖定服務或通用寫入帳本。
- 任何角色若會改動共享的 DB、VPS、GPU、staging、測試帳號或其他資源，都必須先取得資源租用。
- 資源租用至少包含任務、角色、用途、存取模式及釋放條件。租用只代表協作許可，不是技術隔離證據。
- 釋放前確認相關程序停止及必要恢復完成。狀態不明時可以釋放協作占用，但必須標示「狀態未知」，下一位使用者不得直接寫入。
- 既有資源不因租用結束而自動刪除；憑證不得存入任務卡或框架設定。

非阻擋觀察放在當次階段完成卡片的固定小節，不另發留言，也不能阻止階段完成。資源目前的占用者、用途及狀態放在 GitHub Project 的單一 `Resource` 欄位；只保存當前協調資訊，不建立完整租用歷史或新狀態機。

## 10. 規則與專案注入

規則依下列順序提供上下文，後層只補充專案事實，不複製或暗改前層規則：

1. 框架核心文件。
2. 使用者層共同資料。
3. 專案 `.wf/` 補充。
4. 任務資料。

角色、正式階段及研究子狀態各有獨立文件；純機械狀態集中定義。ai-workflow 專案本身也使用 `.wf/` 提供自己的補充規則。

使用者層可以保存穩定的模型使用說明，以及短期的模型可用性／額度備註。短期備註只記來源與最後確認時間；PM 派工前自行確認，過期或不確定即視為未知。第一版不建立額度查詢、自動過期、重置時間計算或模型選擇引擎。

## 11. CLI 與平台邊界

CLI 只負責：

- 載入與呈現規則及必要清單。
- 保存與顯示合法的流程狀態。
- 檢查資料格式、必要章節存在且非空，以及 SHA、分支、CI 等客觀事實。
- 偵測過期寫入並拒絕覆寫。

CLI 不負責：

- 判斷需求、研究、根因、風險、內容品質或模型能力。
- 呼叫、選擇或調度 AI。
- 包含模型 provider、AI adapter、額度引擎或任意工作流規則引擎。

第一版只需要 GitHub 平台介面。核心保存不透明任務識別，不理解其格式；GitHub adapter 可以使用 `repo#issue`。其他平台等出現真實需求後再設計。

需求只限制核心不得依賴 GitHub 專屬型別、CLI 不呼叫 AI、採用專案只維護 `.wf/`，以及規則來源可指向本機開發版本。具體容器、介面切分、欄位歸屬與實作名稱由規劃階段決定。

## 12. GitHub 呈現

- Issue body 保存主要成果契約，使用少量固定章節標題與自由文字。
- CLI 只確認必要章節存在且非空，不解析散文語意，也不要求大型 JSON。
- GitHub Project fields 是階段、狀態、owner、風險、緊急性、期限及當前資源狀態的唯一來源。
- 留言只保存階段完成、需求方裁定、阻塞／解除與結案等對協作有直接價值的事件；不貼移動紀錄、欄位 hash、長篇 CLI 輸出或重複狀態。
- 每張卡指定一位最終需求方。需求方可在對話或 GitHub 裁定；對話中的裁定由 PM 忠實登記裁定者、內容與時間，不得擴張原意。
- 派工內容必須能由適用的框架規則、使用者層資料、Issue body、Project fields、已核定階段卡片與 `.wf/` 重新產生，不依賴 PM 私有對話記憶。

## 13. 模組邊界

第一版模組只能在固定擴充點注入文件、輸入、命令或客觀檢查，不得新增正式階段、狀態、計數器或轉移規則。未來有真實案例需要改變流程形狀時，再以獨立需求設計，不預建任意流程擴充能力。

測試驅動開發等方法可以作為選用模組，不成為所有專案的核心義務。

## 14. 重建與採用

- vNext 在隔離分支重建，並使用本文件定義的輕量人工流程管理自己的工作。
- 舊 CLI、舊卡片格式、舊 trailer 規則及舊狀態機只作歷史參考，不得治理或阻擋 vNext。
- 規劃階段須列出現有 CI 與 ruleset 中仍會作用的舊檢查，並為 vNext 停用、隔離或替換。只有能重新說明其直接保護成果的工程檢查才可保留。
- 舊程式碼只有在直接支持 vNext、沒有舊狀態機相依且比重寫簡單時才重用。
- 框架以版本化套件提供；採用專案只維護 `.wf/`。Git submodule 不作主要安裝方式。本機開發可以讓規則來源指向 checkout。
- 不為 CPBL 或其他單一專案寫入框架耦合。舊版差異過大的專案可以手工升級；第一版不為過時版本建立通用遷移層。

第一版必須包含：採用入口、分層注入、角色與階段文件、研究子狀態、五階段基本流程、需求鎖定、簡潔階段卡、模型資料政策、風險與緊急性、簡潔 GitHub 呈現、正常修正與退回紀錄、假設失效及停止路徑，以及一次外部真實任務試跑。

第一版不包含：任意流程擴充、完整版本升級系統、CPBL 專用邏輯、自動模型呼叫、模型額度引擎、通用遠端寫入復原、大型 mutation 測試系統或舊版相容層。

## 15. 可投入使用的驗收

一次外部專案的真實任務是主要採用驗收，但不宣稱覆蓋所有例外情境。試跑前記錄預期成果、人工介入點與可接受流程成本；完成後記錄：

- 各階段確認次數與需求方閱讀負擔。
- 是否需要框架外的人工補救。
- 是否發生方向偏移或跨階段越權。
- 成果與直接證據是否容易檢視。
- 不同模型的分工與獨立審核是否真正提供額外視角。
- 需求方是否認為比直接管理 AI 更省力。

未自然發生的假設失效、阻塞與停止路徑，只作少量有界演練，不建立大型驗證框架。試跑未使用的資源租用或選用模組標記為尚未驗證，不得宣稱成熟。

vNext 只有在外部任務完整走完、每階段確認保持簡短、成果獲得獨立跨家族審核、專案注入正確、GitHub 畫面可在一個畫面理解、非阻擋問題沒有擴張任務，而且需求方確認使用成本較低後，才可視為具備首次採用條件。

## 16. 留給規劃階段

以下項目不得在需求階段提前鎖定：

- 核心物件、service、adapter 或 context 的具體名稱與切分。
- GitHub fields、階段卡、Resource 欄位及版本值的精確格式。
- CI 隔離、分支策略、套件格式及規則來源的實作方式。
- 資源租用資料的技術儲存方式與平台限制。
- CLI 命令名稱、內部資料結構與程式碼重用清單。
- 外部試跑的具體專案與任務。

規劃必須遵守本文件的成果與邊界，不能藉技術選擇重新引入舊版複雜度。
