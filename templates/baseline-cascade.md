# Baseline Change Cascade Runbook

> canonical §3「checkpoint 發現設計／需求變更時，先更新父卡基線、標註受影響子卡與重新核可，再繼續；禁止只在子卡內靜默改方向」的操作程序。適用於 Initiative 子卡序列，以及無父卡但共享同一 spec／契約的卡片鏈。

## 角色與載體

- **基線載體**：Initiative 父卡的 `spec 基線：v<N>` 與「基線變更紀錄」章節。無父卡的卡片鏈以共同 spec 檔為載體（檔頂記版本與變更紀錄）；同一鏈**第一次發生 cascade 時就地補建 Initiative 父卡**收依賴圖，不再以卡片間口耳相傳。
- **觸發者**＝發現偏離的執行者；**評估者**＝規劃者（或 Coordinator）；**核可者**＝需求方。三者職責不可合併於觸發者一人。

## 程序

1. **凍結**：執行中發現交付需偏離已核可基線（Discovery／Design／Plan spec，或上游卡對下游卡的契約）時，執行者停止**受影響部分**的實作，在卡 Log 與 lifecycle event 留 `baseline-change-request`：偏離內容、理由、證據、預估影響面。不受影響部分可續作；**執行者不得自行修改基線文件後繼續實作**。
2. **影響評估**：評估者對照父卡依賴圖，逐一標注受影響卡的影響級別與處置：

   | 級別 | 判準 | 處置 |
   |---|---|---|
   | `none` | 介面／契約不變 | 不動 |
   | `scope` | 驗收條件或範圍需改 | 更新卡面，`spec 基線` 欄 bump 至 v\<N+1\> |
   | `blocked` | 實作前提失效 | 轉 `⏸阻塞`；解除條件＝新基線核可 |
   | `invalidated` | 方向失效 | 需求方裁定 `🛑已停止` 或退回 Discovery／Design Gate |

3. **基線遞增**：父卡 `spec 基線` v\<N\> → v\<N+1\>，「基線變更紀錄」新增一行：日期、變更摘要、觸發卡、受影響卡與級別、核可者。**需求方核可前新基線不生效**；等待期間觸發卡只能續作不受影響部分或轉 `⏸阻塞`。
4. **傳播**：核可後——Backlog 中的受影響卡由規劃者更新卡面與基線欄；**執行中**的受影響卡由 Coordinator 通知其執行者確認 in-flight 工作是否受波及，受波及即 handoff 或轉阻塞；**已合併卡不回改**，缺口另開 follow-up 卡。
5. **查核防線**：查核者驗收任何子卡時，核對卡面 `spec 基線` 版本＝父卡當前版本；不一致即退回（防止舊基線交付）。專案若有查核提示詞產生工具，應自動帶入父卡當前基線版本。

## 反模式

- 在子卡內改 spec 再事後告知（靜默改向）。
- 用聊天訊息或口頭共識代替「基線變更紀錄」。
- 跳過需求方核可直接改下游卡卡面。
- 把 `invalidated` 降級為 `scope` 以避免回 Gate（影響級別由評估者判定並留痕，非觸發者自判）。
